# Standalone skill generator inputs

`tools/build-standalone-skill.sh` turns this plugin's ticket-creation workflow into a single, self-contained, host-neutral Agent Skill, `create-ticket/` by default or `<skill-name>/` with `--name` (a `SKILL.md` plus `references/`). The generated skill needs no plugin, no hooks and no custom agent files (Python 3 only to read `.xlsx` sources, and, when present, to convert a ticket to HTML and to check the text a remote destination stored), and it names tools by role (see `## Tool roles` below) rather than by any host's tool name: copy the directory into the skill root the host reads (`.github/skills/`, `.claude/skills/` or `.agents/skills/`) and invoke it by name. The generator keeps its historical name; its output was first shaped for GitHub Copilot CLI and has not been run live on any host yet.

```bash
bash tools/build-standalone-skill.sh --out <dir>                       # writes <dir>/create-ticket/
bash tools/build-standalone-skill.sh --out <dir> --name <skill-name>   # writes <dir>/<skill-name>/
bash tools/build-standalone-skill.sh --out <dir> --force               # replaces <dir>/<skill-name>/ only if it holds a generated skill
bash tools/build-standalone-skill.sh --help
```

The output is never committed (there is no golden copy). Its correctness is enforced by the build's own exit audit and by `tests/test-standalone-skill-build.sh`, which builds into a temporary directory and re-checks the result independently.

## What the generator does

For every file in `files.tsv` it applies four layers, in this order:

1. **Sections** (`drop-sections.txt`, `overrides/*.md`): drop or replace a section by its exact heading line, insert new content before a heading, or append content at the end of a file. A section runs to the next heading of the same or a higher level at the same fence depth, so a heading inside a fenced template never swallows the fence that closes it.
2. **Paragraphs** (`drop-paragraphs.txt`): drop by anchor ERE. A hit on a list item drops that item, a hit on a table row or on a line inside a fenced block drops that line, and any other hit drops the whole paragraph.
3. **Substitutions** (`substitutions.tsv`): `sed -E` rewrites applied in file order. Specific sentence rewrites come first, then paths, tool names and the pipeline role phrases.
4. **Exit audit**: `denylist.txt` (any hit fails), the host tool names of `tool-vocabulary.txt` (Claude Code and GitHub Copilot names alike), a non-English (CJK) byte scan, link and `references/...` path resolution, balanced inline code spans, the frontmatter contract (`name`, `description` length, no `allowed-tools`), rubric parity for `references/ac-quality-criteria.md` (same Gate headings, same Terminology entry count, word count within 5% of the source), and the variant check (no other form of the skill's name that the check covers beside the token `create-ticket`, see the `--name` paragraph below). The rubric files are zero-loss in intent: never delete a gate, an example or a rule; rename tokens, and restate a host-bound sentence (a role, a tool-access rule, a file or setting this host does not have) so it is true on any host.

Agent files listed under `references/agents/` lose their frontmatter; the body is the prompt the generated skill hands to a general-purpose subagent through the host's subagent tool.

A later naming pass added `--name <skill-name>` (default `create-ticket`), so the generated skill can carry any valid name, including one that says nothing about tickets. A name is 1 to 64 lowercase ASCII letters, digits and hyphens, with no hyphen first, last or next to another (`^[a-z0-9]+(-[a-z0-9]+)*$`: the Agent Skills rule kept to ASCII, because the name sits inside shell templates and regular expressions). The names the skill's text uses for its roles (`planner`, `researcher`, `decomposer`, `ticket-evaluator`, `evaluator`, `orchestrator`: the orchestrator that runs the skill and the roles it spawns) are reserved, since a skill of that name could not be told apart from the role; a name a YAML reader takes for a number, a boolean, null or a date (`123`, `true`, `yes`, `1e3`, `2024-01-01`, `2024-1-1`) is refused, since the frontmatter writes the name as a plain scalar; and a host tool name that the exit audit's foreign-tool-name rule rejects (`bash`, `view`) is refused too: a probe text holds the name in each place it takes in the tree (an invocation, a backticked name, a skill-root path, the scratch directory, an `ERROR:` prefix, prose, a heading, the frontmatter `name:`), and a foreign-tool-name finding that the same probe with `create-ticket` does not produce refuses the name. Every refusal exits 2 before anything is written. The denylist is not applied to the name: it finds vocabulary leaked from the plugin into the generated text, the canonical text has already passed every row, and a row that only the chosen name trips is a resemblance, not a leak. So a name that resembles a word of the source plugin (`hooks`, `brief`, `test-plan`), a command or skill folder a particular host reserves, or a product is not refused, because the generator is host-neutral and that choice is the user's: check the host's documentation before choosing a name it may already use. The skill also prints the name as the subject of its own `ERROR: <name> ...` lines and writes it as `` `<name>` `` and `/<name>` in its text, so a name that is also an ordinary word of that text (`source`, `destination`, `findings`) or a command the skill runs (`git`, `grep`) reads ambiguously there; such names are accepted, and the choice is the user's. The manifests keep the canonical name `create-ticket` (the upstream paths and the text every rule was written against): layers 1-4 and the whole exit audit run on the canonical text, whose variant check fails the build on another letter case, an underscore or no separator (`Create-Ticket`, `create_ticket`, `createTicket`), on `create-ticket` glued to an ASCII letter, digit, hyphen or underscore (`create-tickets`, `pre-create-ticket`; the scratch directory `create-ticket-scratch` is the one allowed compound), on the name wrapped over a line end (`create-` last on a line, trailing blanks aside, and `ticket` first on the next, leading punctuation aside), on a generated file named after it (the rename does not rename files), and on an upstream path `skills/create-ticket`, with or without a trailing slash, that is not a host skill root such as `.claude/skills/create-ticket/` (the dot first in its path segment). A form that differs from the name by markup, a character entity, a non-ASCII hyphen or an invisible character is out of the check's reach, and so are the two words with a space between them, since the text holds the prose "Create tickets from the supplied sources"; such a form in a future source edit has to be caught in review. Only a tree whose exit audit is clean is renamed, by one `sed` pass per file that replaces every `create-ticket`. A name audit then checks the renamed tree: per file, the occurrences of the name, less those the canonical text already held, equal the `create-ticket` occurrences counted before the pass; no `create-ticket` is left outside an occurrence of the name; the frontmatter `name` equals the name and the directory name; the description still fits 1,024 characters (the finding says when the name made it too long); and the foreign tool names and the inline code spans are clean again (the denylist is not run again, for the reason above). A finding exits 1 and is attributed to the name. The tree is built and audited in a staging directory under `$TMPDIR` (or `/tmp`), and `<out>/<name>/` is created or replaced only when every audit is clean: a failed audit keeps the failed tree in the staging directory its message names, and the previous skill at `<out>/<name>/` survives a failed build unchanged. `--force` replaces only a directory that holds a skill this generator wrote (the frontmatter of its `SKILL.md` holds the line `  source: generated skill; do not edit by hand`, which every generated tree carries; the same line anywhere else in the file does not count); any other non-empty directory, a directory that cannot be read, and a file or a link that is not a directory, is refused with exit 2, with or without `--force`, and nothing else under `<out>` is ever removed. The audited tree is first moved next to `<out>/<name>/`; the previous tree is then renamed aside and the new one renamed into place with signals held off, so a publish that fails or is interrupted leaves either the previous skill or the new one, and a previous tree that cannot be removed completely is named in a `WARNING:`. The text that says what the skill does never relies on the name: the description and the sentence under the top heading of `SKILL.md` say that the skill drafts implementation tickets, grades them against a quality rubric and delivers them, the description adds that the name used as an ordinary word does not name the skill, the role prompts name the skill they must not run as "the `<name>` skill (the skill that spawned you)", and the generated README tells the reader never to change the directory name or the `name` by hand, since the skill's own paths, scratch directory and messages carry it. The test builds the tree as `zq-x7` and finds no `create-ticket`, `create_ticket` or `createTicket` in it in any letter case; with the exit audit's variant check on the canonical text, that zero-leftover check shows no occurrence in a form the variant check covers was missed. It then maps `zq-x7` back to `create-ticket` in every file and compares the result byte for byte with the default build from the same source, which shows the rename changed nothing else (a missed occurrence would map back to itself, so the round trip alone cannot show that). It does the same for `create-ticket-v2`, checks that `--name create-ticket` is the default build, builds `ticket` (a word the canonical text already holds), a 64-character name and names that resemble plugin words or folders (`hooks`, `brief`, `test-plan`, `best-effort`, `home`), refuses a 65-character name, the invalid and reserved names, names YAML would not read as a string and a foreign tool name with exit 2 and nothing written (also against an absent `--out`), checks that `--force` leaves sibling directories alone, refuses a non-generated directory, a file and a dangling link with or without `--force`, keeps the previous skill byte for byte through a failed build and leaves nothing behind after a missing source file, builds a relative `--out` under an exported `CDPATH`, classifies every occurrence of `create-ticket` in the default tree by its context (so a new context has to be reviewed before it ships), proves that the variant check reports each other spelling planted in a copied source and a file named after the skill, and proves that the name audit catches a foreign tool name the probe was switched off for, a rename that missed occurrences and a description the name made too long. CI runs `tests/test-standalone-skill-powershell.ps1` on both the default tree and the `zq-x7` tree; the test reads the skill name from the `name:` line of `SKILL.md`.

## Maintenance model

Re-run the build after any change to the shipped sources. If the audit fails, add a manifest line: a substitution for a renamed token, a paragraph or section drop for host-only machinery, or an override for a section that needs a host-specific rewrite. Every manifest line must match at least once in its scope; a stale line fails the build too, so delete the line when its source text is gone.

## Manifest formats

All manifests are plain text; `#` comment lines and blank lines are ignored. Patterns are POSIX ERE evaluated with `LC_ALL=C` (no `\b`, `\s` or `\w` in substitutions, since BSD `sed -E` lacks them).

| File | Line format |
|---|---|
| `files.tsv` | `<destination under the skill directory><TAB><source relative to --src>`, or `-` as the source for a file with no plugin source (it starts empty, one `append` override supplies its whole content, and a `-` file left empty fails the build) |
| `drop-sections.txt` | `<destination glob><TAB><exact heading line>` |
| `drop-paragraphs.txt` | `<destination glob><TAB><anchor ERE>` |
| `substitutions.tsv` | `<ERE><TAB><replacement>[<TAB><destination glob>]` (sed replacement syntax; default scope is every file) |
| `denylist.txt` | `<ERE>` |
| `tool-vocabulary.txt` | `deny <name>` |

A `substitutions.tsv` row that should be scoped but lost the TAB before its target collapses into a two-field row: it applies to every file and glues the target's name onto the replacement text. The build therefore refuses (exit 2, naming the line number) any two-field row whose replacement ends in `SKILL.md`, `README.md` or `references/<path>.md` directly preceded by sentence punctuation: one of `.` `)` `]` `!` `?` `:` `;` `,` `*` `` ` `` `'` `"`. A replacement that is itself a path is preceded by a backreference, a letter or a space (`\1SKILL.md`, `\1references/interview-templates.md`) and passes; a replacement that must end in punctuation followed by such a path is written with an explicit `*` target instead. The test also checks the generated tree for a sentence end glued to a generated file path.

An override file starts with three header lines and a `---` separator; everything after the separator is the content:

```text
target: <destination> [<destination> ...]
heading: <exact heading line> | (frontmatter) | (end of file)
mode: replace | before | after | append
---
<content>
```

`replace` swaps the whole section (heading included) for the content, `before` / `after` insert the content around the section, and `append` adds the content at the end of the file. The frontmatter override may use the placeholders `@SOURCE_VERSION@`, filled from `.claude-plugin/plugin.json`, and `@SOURCE_COMMIT@`, filled with the short commit of `--src` (`git rev-parse --short HEAD`; the literal `unknown` when `--src` is not a git repository or git is unavailable).

## Delivery and destinations

The generated skill is decoupled from this repository's own backlog layout: producing the tickets (Phases 1-4, the four agent prompts, the rubric and grading files) is unchanged, while the upstream write path is replaced whole by a `## Delivery` section (`overrides/skill-delivery.md`) and the destination adapters live in `references/destinations.md`, a file with no upstream source (`overrides/destinations.md`). The skill takes `destination=local:<dir>` (default `local:tickets`), `destination=mcp:<server>[/<tool>]`, `destination=api:<url>`, `destination=browser:<url>` or `destination=cli:<command template>`. The denylist rejects the plugin name, its backlog paths, `{ticket-dir}` and the dropped investigation-reuse key, so an upstream edit that reintroduces them fails the build.

A later body-fidelity pass made the delivered text the whole ticket, moved by programs: Phase 4 records the draft file each evaluator round graded and reads every inlined draft from it, a planner's draft file holds only the ticket (`overrides/skill-phase4-graded-draft.md`, `overrides/spawn-prompts-draft-file.md`), a retry draft that lost a heading prints a `WARNING:` (`overrides/spawn-prompts-section-check.md`), Step DL-2 builds `{scratch}/final-{i}.md` by `cp` and file-edit replacements only, every adapter copies that file again instead of writing the ticket out, and a heading check stops a ticket whose sections were lost on the way (`references/destinations.md` **Whole text, never re-typed**, **Logical ids**, **Heading check**). The new `body_format=markdown|markdown-escaped|html` option converts the text for the content field by a program (`sed`, or the new shipped `scripts/ticket_body.py`, `overrides/scripts-ticket-body.md`, a standard-library Markdown-to-HTML converter that checks its own output), derived from what the orchestrator knows of the platform when the destination comes from a URL (**Content-field markup**), and after every remote create `ticket_body.py check` compares the words the platform stored with the ticket and stops the run on an incomplete text (**Stored text check**, counted on the Final summary's `Body:` line). The same pass added `auth_scheme=basic-token` (and `source_auth_scheme=basic-token`) for a variable that holds only a token, sent as the password of an empty user name, trims a CR from the title file, keeps a derived URL's query string in the request while printing it as `?[query-omitted]`, and removes the scratch directory with `rm -rf` plus an existence test. The test drives the converter and the check on fixture tickets it writes itself (Japanese text, angle-bracket placeholders, escaped pipes, fenced blocks, comment markers, CRLF, a byte order mark, JSON responses, a JSON document inside a text or a JSON string, a body returned twice as two values or in one text, a page text without a link target, a body cut off after its start, the three thresholds at their limits).

A later shell-dialect pass made every shell step run under PowerShell as well as in a POSIX shell. Pre-computed Context records the shell tool's dialect on a new `Shell:` line, taken from the host's description of its shell or from one probe that both dialects accept (`echo $PSVersionTable.PSVersion.Major`). Host notes state the rule once (**Shell dialect**): under PowerShell no POSIX form ever runs, because several POSIX command names are aliases of other cmdlets there and `rmdir` can delete a directory with its content. The new generated `references/shell-powershell.md` (`overrides/shell-powershell.md`) gives general rules and one entry per shell step, each with a `PS-<AREA>-<n>` id, the POSIX form quoted verbatim and a form written for Windows PowerShell 5.1 and PowerShell 7 alike. Those forms use .NET file calls with absolute paths and UTF-8 without a byte order mark, and they never use `jq` or `sed` (a JSON field, the request body and both content-field conversions are done in PowerShell itself). They print an ASCII token for each outcome, write text that can hold other characters to a file, and remove directories only through `Remove-Item -Recurse` on the run's own scratch path and the .NET call that refuses a directory that is not empty. The same pass made the POSIX forms survive login-shell options (`>|`, `command cp` and `command mv`, an existence test before `>>`, an unmatched collision pattern read as no match). It also reads drive and network share paths as paths, chooses the Python interpreter by running `--version` on `python3`, `python` and `py -3`, and lets the workbook converter write its text itself (`--out`). The build test checks the PowerShell file statically (id headings, no syntax of PowerShell 7 only, no POSIX alias, no file-writing cmdlet, every POSIX form of the tree covered) and runs the POSIX forms under zsh, sh and bash with no-clobber and interactive aliases. `tests/test-standalone-skill-powershell.ps1` takes each PowerShell form from a built tree by its id and runs it against fixtures; CI runs it on Windows under both `shell: powershell` and `shell: pwsh`, on the tree the Ubuntu job builds, with `-RequireAll`, so a form skipped for a missing program fails the job.

## Sources (intake)

`source=<spec>` tokens (repeatable, any mode) let the user hand the skill its input material instead of a pre-written brief or findings file: `file:<path>` (Markdown, text, CSV, TSV, JSON, YAML, or an `.xlsx` workbook read as a workbook), `dir:<path>`, `mcp:<server>/<tool>[?name=value]` (one read-only call) and `api:<url>` (one `GET`, `source_auth_env=` for the token). The contract lives in `references/sources.md` (`overrides/sources.md`, a file with no upstream source), the sequence in SKILL.md `## Intake` (`overrides/skill-intake.md`), and the partition decision in the decomposer (`overrides/decomposer-source-dossier.md`, `overrides/spec-decomposer-source-dossier.md`): the decomposer judges whether one source enumerates the work units (then they map to tickets one-to-one) or whether every source is context, and reports `Partition basis`. The workbook converter `scripts/xlsx_to_text.py` (`overrides/scripts-xlsx-to-text.md`) uses only the Python 3 standard library; the test builds a fixture workbook with the same library and checks its output. The optional sheet renderer `scripts/xlsx_render.py` (`overrides/scripts-xlsx-render.md`) also uses only the standard library; the test drives it with stand-in renderer programs it writes itself, because a spreadsheet application or LibreOffice is not assumed on the build host. The upstream `/create-ticket` has no `source=`; the feature exists only in the generated skill.

Later additions on the same layer: the default destination is `local:.local/tickets`; `parent=<id>` links delivered items to an existing platform item through the create tool's parent-link parameter (found by its description) or the `{parent}` template placeholder; `?sheet=<name>` on an `.xlsx` source selects worksheets (`--sheet` on the converter); the request's input and output may be stated in prose, resolved to the canonical tokens before the token scan and echoed as a `Resolved:` line; user paths and names follow a character exclusion rule instead of an ASCII-only pattern, so names in any script are accepted; the web URL of an item on a platform whose HTTP API the orchestrator knows with confidence, named in prose as an input or as the item to create the tickets under, is turned into the two `api:` adapters with the endpoint, body template, parent link and content field derived, printed on `Resolved:` and `Derived:` lines and confirmed before any create unless `confirm=yes` is typed or implied (new options `source_content_path=`, `source_auth_scheme=`, `content_type=`, `auth_scheme=`; `{parent}` may sit inside a longer template string). A URL named in prose, as an input or as the item to create the tickets under, is reached through the best of several access channels (an MCP server of the session, the platform's signed-in command-line client as the new `cli:` source and destination kinds, the HTTP API as the two `api:` adapters, the session's optional browser tool as the new `browser:` kinds, and for an input a plain `GET` of the URL as typed), chosen by the orchestrator's best guess, which is printed on `Derived:` lines before it runs, logged on `Tried:` lines when an attempt fails (a sign-in page returned with a 2xx status counts as failed) and, for an output, verified by a read-only `Probe:` of the parent item before the first create; sign-ins already on the machine are reused (a named or conventionally named token variable, checked only with the set/unset probe, a signed-in client, a signed-in browser), and when none is at hand the skill asks once or stops with an `ERROR:` that spells out the re-run tokens. The workbook converter is structure-aware: besides cell values it prints in-cell line breaks as `<br>`, merge markers, `~~text~~` strikethrough and hidden-row and hidden-column markers, adds `### Notes`, `### Shapes` and `### Images` sections per sheet, prints a sparse or block-merged sheet in a `cells` layout (`--layout auto`, the default), and with `--extract-media` writes the pictures to `{scratch}/sources/S<n>-media`, so the structure of a workbook used as a document stays visible in the source dossier. `render=auto|off|excel|soffice` adds an optional PDF render of a structured workbook through a chain of renderers that may be installed on the host (a spreadsheet application driven through its automation interface without a window and without saving, then LibreOffice), recorded as a `Rendered:` line at the end of the source's dossier text, and `file:` also accepts `.pdf` and image files, which the orchestrator transcribes through the host's file-read tool (no OCR).

A later audit pass made the rules agree and relaxed the strict ones: `rounds=<N>` (1-5, default 3) and `max_tickets=<N>` (1-30, default 20, carried to the decomposer as a `Max tickets:` line, with the dropped units written to `{scratch}/overflow-findings.md` as a findings document) are new options; a split run delivers every ticket whose exhausted-retry escalation ended in proceed and stops only on a stop, with one ask-user question for all still-failing tickets; a `source=` or `destination=` URL without a kind is resolved like a URL in prose (`api:` typed stays verbatim), derived content paths and token variables belong to their own source, and an MCP-derived destination may guess the create tool's other parameters; on a host with no ask-user tool `confirm=yes` is implied (printed as a `NOTE:` after the destination preflight and in the Final summary) unless the new `confirm=no` is passed, in which case the preflight stops a remote run that could never confirm, while an ask-user tool that errors or is denied implies nothing; a "no" prints `remote delivery declined`; a failed mandatory spawn is retried once; any text file (no NUL byte in its first 8,000 bytes) is a `file:` source, `dir:` descends five levels (deeper directories are reported with a `WARNING:`, never dropped silently), the intake total truncates instead of refusing, only the specs the request carries count toward the 50-source `ERROR:` (a `dir:` expansion and follow-up reads stop at the cap with a `WARNING:` instead), a platform item URL allows up to 20 follow-up reads, `local:` and `template=` paths may be absolute or `~`-prefixed, a backslash in a path reads as `/`, and a slug that is not kebab-case is normalized with a `WARNING:`.

## Skill README

The run scratch directory (`{scratch}`, every transient file of a run) is created with `mktemp -d` under `.local/<skill-name>-scratch/` (`.local/create-ticket-scratch/` by default) inside the working directory, never under a system temporary directory, and the line `**/.local/*` is appended to the repository's root `.gitignore` when that exact line is missing (which also ignores the default destination `.local/tickets`): the first live run showed that a host may confine the file tools of the orchestrator and of every subagent to the working directory, so a scratch outside it cannot be written or cannot be read back. The same run showed the researcher running the product's test suite and a delete command on a directory of its own, so `overrides/agents-side-effect-ban.md` names execution of the product and delete commands explicitly, and Phase 4 now spawns every ticket's evaluator in one message. The skill used to delete nothing and leave every scratch directory behind; it now removes `{scratch}` as the last step of a clean run (`keep_scratch=yes` keeps it, and an `ERROR:`, a `FAIL` verdict or overflow findings keep it too) with `rm -rf "{scratch}"` on the exact relative path `mktemp` printed (the `-f` keeps a login shell that aliases `rm` to an interactive form from asking a question nobody answers), an existence test of the directory that turns a directory still present into the removal `WARNING:`, then `rmdir` on the two parents, ignoring an `rmdir` that finds a parent not empty. Those delete commands, run by the orchestrator alone, are the skill's only delete commands; the delete ban on the researcher and planner roles is unchanged. A run also delivers to exactly one destination: the default `local:.local/tickets` applies only when the request names no output at all, never as a fallback for an output that cannot be resolved or reached, and a destination other than `local:` saves no local copy of any ticket. A live run that delivered remotely also saved a local copy and ended with a free-form recap, so both are now stated as rules: no local copy outside `{scratch}`, and the `### Final summary` block is printed in its stated format and never replaced by a free-form recap.

The generated directory ships its own `README.md` (`overrides/readme.md`, a file with no upstream source): install, host requirements, usage, the three modes, sources, destinations, the other options, the verdicts, the file map and the limits, written for the person who receives the directory and never sees this repository. It is subject to the same exit audit as every generated file (no host name, no upstream name, every relative link resolves), and the test checks its sections.

## Self-contained vocabulary

Every term in the generated tree must be resolvable from the tree alone. The denylist therefore also rejects plugin-internal jargon that nothing in the tree defines: the implementation-time eval panel and its lens names, the evidence-floor shorthands, the lettered failure-class codes, the plugin's downstream role names (the rubric defines one phrase instead, the **downstream implementer/verifier**), `load-bearing`, `plan.md`, a mid-sentence `Read` (the Claude Code tool name), the generator's own paths and the old `Stopped:` message. The rubric's kill switches are real on this host: a `constraint_<key>=off` request token turns a gate off for the whole run, and Argument Parsing rejects an unknown key.

## Tool roles

The generated text never names a host's tool. It names nine roles, defined once in `SKILL.md` `## Host notes` (**Tool roles**): the file-read tool, the file-write tool, the file-edit tool, the search tools, the shell tool, the URL-fetch tool, the subagent tool, the ask-user tool and the browser tool (optional, never required). The skill resolves each role to one concrete tool of the host before Phase 1; a host without a subagent tool takes the degraded branch (`SELF-EVALUATED`), a host without an ask-user tool takes the non-interactive fallbacks, and a host without a browser tool never uses the `browser:` channel. The frontmatter `compatibility:` states the same requirements without naming a host, and the denylist rejects `Copilot`, `GitHub.com`, `cloud agent`, `agent_type` and the "on this surface" phrasing of the earlier Copilot-bound output, while `tool-vocabulary.txt` rejects every backticked Claude Code and GitHub Copilot tool name. When a new manifest line has to mention a tool, write the role phrase ("read it with the file-read tool", "via the subagent tool"), never a product's tool name. The vocabulary denylist matches the exact backticked token, so a future upstream example that legitimately backticks a common word such as `create`, `edit`, `view` or `task` fails the build with a "foreign tool name" finding: restate the example or re-anchor the row, as for any stale manifest line.
