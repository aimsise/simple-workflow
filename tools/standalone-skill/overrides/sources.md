# Sources (`source=<spec>`)

A source is any material the user hands to `/create-ticket` besides the request text: a document, a spreadsheet, a directory of such files, the result of a read-only MCP tool, a document fetched over HTTP, the output of a read-only command of a command-line client, or the text of a page read through the browser tool. Sources are read during **Intake** (SKILL.md `## Intake`), after the destination preflight and the creation of `{scratch}`, and before Phase 1. Intake normalizes every source to one text file under `{scratch}/sources/`, concatenates them into the **source dossier**, and the rest of the run reads only that dossier: the researcher (as context about the work), the Phase 2 interview (questions the dossier already answers are not asked), the decomposer (which decides whether one source is the **partition basis**, the list of work units the tickets map onto one-to-one, or whether every source is context only) and the planner (excerpts only). The ticket-evaluator never sees it.

`source=` tokens combine with every mode. With `brief=` or `findings=` the dossier is context only and the partition basis stays with the brief-derived or findings-enumerated units; with a bare description, or with no description at all, the decomposer judges the partition basis from the dossier (see `## Partition basis`).

## Rules for every source

- **Read-only.** Intake never writes anywhere but `{scratch}/sources/`, never modifies a source, and never calls a tool or endpoint, runs a command or submits a page that creates, updates, deletes, sends or posts anything. A source that cannot be read stops the run before Phase 1 with the `ERROR:` line of its kind; nothing has been delivered and the `local:` counter is unchanged.
- **Order and ids.** Sources are numbered `S1`, `S2`, ... in request order; a `dir:` source expands into one id per file, in sorted file order, at its position. Every later reference to a source uses its id.
- **Pattern-checked input.** A `file:` or `dir:` path may be absolute (it is the user's own file) and may hold any letters of any script, but follows the character rule of SKILL.md Argument Parsing (no double quote, backtick, `$`, backslash or control character; whitespace only inside a double-quoted token or in a value resolved from prose); a `file:` spec may end in a query `?sheet=<name>[&sheet=<name>]`, split off before the check and allowed only on an `.xlsx` file (any other key, or a query on another kind → `ERROR: source=file:<path>: unknown option <key> (only sheet= on an .xlsx file)`), each sheet name following the same rule (the query starts at the last `?` of the spec; a `&` separates two `sheet=` values, so a sheet name that itself contains `&` or `?` cannot be written in token form and is given in prose, which carries it whole); an `mcp:` spec and an `api:` URL follow the patterns of the same kinds in `references/destinations.md`, a `browser:` URL follows the `api:` URL pattern, and a `cli:` command follows the `cli:` exemption of that character rule (`## cli:<command>`); a `source_auth_env=<VAR>` name matches `^[A-Za-z_][A-Za-z0-9_]*$`. A value that does not match → `ERROR: source=<spec without query> contains characters this skill does not accept` and stop, before anything is read. A `source_content_path=` value is not checked here: it follows the `id_path=` pattern of the `api:` destination and has its own `ERROR: source api: unusable source_content_path <path>` line, also raised before anything is read (`## api:<url>`), for a `cli:` source as well. Every path in a shell command is double-quoted.
- **No secrets in text.** The value of the variable `source_auth_env=` names never appears in a prompt, ticket, summary, error line, log, file or command line; a shell command refers to it only as `$VAR`, and the `api:` fetch passes the header through `curl -K -` exactly as the `api:` destination does. A `cli:` command refers to a variable only as `$VAR`, expanded by the shell, never by the skill. An `api:` origin is recorded and printed without its query string.
- **Normalized file.** Source `S<n>` becomes `{scratch}/sources/S<n>.md`, written with the file-write tool:

```text
Source: S<n>
Kind: file | dir | mcp | api | cli | browser
Origin: <the path (with its ?sheet= query for a workbook), or mcp:<server>/<tool>?<query>, or the URL without its query string (api, browser), or the command (cli)>
Derived from: <the item URL without its query string; a source derived from a platform item URL only>
Fetched: <UTC time of the read>
Chars: <character count of the content below>
Truncated: no | yes

<content>
```

  The `Derived from:` line is written only for a source that Prose resolution derived from the web URL of a platform item (`### A platform item named by URL in prose`) through a derived channel: an `api:` read endpoint, a `cli:` command or a `browser:` page, never a plain `GET` of the URL as typed. Its `Kind:` and `Origin:` are those of the channel whose attempt succeeded (the derived endpoint without its query string, the command, or the page URL without its query string), and `Derived from:` names the item URL the user gave. Every other source has no such line, so its header block is six lines (`Source:` to `Truncated:`) and a derived source's is seven. `Chars:` counts the content below the blank line only, never the header, as for every source. `Origin:` for a `cli:` source is the command as run, with a home-directory prefix in it written as `~` and every variable as its `$NAME` reference. `Origin:` for a `file:` or `dir:` path is the path as typed when it is relative; an absolute path is written with the home-directory prefix replaced by `~` (an absolute path outside the home directory is written as typed), and that same form is used wherever the origin is repeated (the dossier index, the `{intent}` line, the planner excerpts, the ticket's `Sources:` line, the Final summary), so no home path reaches a prompt, a ticket or a destination. The `Source:` line is line 1; every locator (`## Locators and excerpts`) counts lines of this file. A `.md` / `.markdown` file is copied verbatim. Any other text kind, an MCP result, an HTTP body, a command's output and a page's text are placed inside one fenced code block (info string `text`) so their own markup cannot open or close a section of the dossier. The output of the `.xlsx` converter is Markdown already and is copied verbatim, followed by its `Rendered:` line (**Sheet rendering (optional)**); a `.pdf` or image transcription is placed inside one fenced block after its `[transcribed ...]` line (`## file:<path>`).
- **Caps.** A source whose content exceeds **60,000 characters** is cut at the last line boundary before the limit, followed by the line `[truncated: source S<n> exceeds 60000 characters; <k> characters dropped]`, and its header says `Truncated: yes`; the `.xlsx` converter applies its own row, column and character caps and marks each one with a `[truncated: ...]` line, which also sets `Truncated: yes`. When the sum of all normalized files exceeds **150,000 characters**, print `ERROR: sources exceed the intake limit (<total> characters > 150000; largest: S<a> <chars>, S<b> <chars>, S<c> <chars>); narrow the inputs` and stop. Every truncated source is also reported once as `WARNING: source S<n> (<origin>) was truncated at the intake cap` and repeated in the Final summary.
- **Count.** More than 50 sources after `dir:` expansion → `ERROR: more than 50 sources after directory expansion; narrow the inputs` and stop.

## Writing a source

A `source=` token carries one spec or a comma-separated list of specs, and a spec may omit its kind. Both are resolved right after the character rule has passed on the whole value and before any other check; every check, cap and `ERROR:` line of this file then applies to each resolved spec exactly as if it had been typed in its own `source=` token with its kind, and the 50-source cap counts resolved specs. Whether a path exists is tested with the shell tool running `[ -e "<path>" ]` (a directory: `[ -d "<path>" ]`), the path double-quoted, never before the character rule has passed.

1. **List split.** A value that begins with `cli:` is always one spec: a command may hold commas. Otherwise, when the whole value, with any kind prefix removed and any `?sheet=` query split off, names an existing file or directory, it is one spec (a file name that contains a comma stays whole). Otherwise split the value at every comma and walk the pieces left to right: a piece that begins with a kind prefix (`file:`, `dir:`, `mcp:`, `api:`, `cli:`, `browser:`), begins with `http://` or `https://`, or, with its `?sheet=` query split off, names an existing file or directory starts a new spec; any other piece is joined back to the spec before it together with its comma, so a comma inside a URL or an MCP query value stays where it was, and a list item that names nothing makes the joined spec fail its own check instead of disappearing. Empty pieces (two commas in a row, a trailing comma) are dropped. Whitespace never separates specs: in `source=a.md b.md` only `a.md` is a source and `b.md` stays in the request text, so several sources are written `source=a.md,b.md`, as repeated tokens, or in prose.
2. **Kind inference.** A spec that begins with a kind prefix keeps it. A spec that begins with `http://` or `https://` is `api:`. A spec whose text before its first `:` is a scheme-like word (a letter followed by letters, digits, `+`, `-` or `.`) that names none of the six kinds → the unknown source kind `ERROR:` of SKILL.md Argument Parsing, so a mistyped kind (`fiel:a.md`) is caught and never read as a path; a path whose first segment contains a `:` is therefore written with `file:`. Any other spec is a path: an existing directory → `dir:`, anything else → `file:` (a missing path then stops with the `file:` not-found `ERROR:`). `mcp:` is never inferred: whether a name is an MCP server depends on the servers connected to the session, so the same text would mean a server in one session and a path in another; an MCP source is written with `mcp:` or stated in prose (`### An MCP item named in prose`). `cli:` and `browser:` are never inferred either: a bare URL stays `api:`, and a command or a page read through the browser is written with its kind or stated in prose (`### A platform item named by URL in prose`).
3. **Echo.** When a token was split or a kind was inferred, the `Resolved:` line of SKILL.md Argument Parsing lists every resolved spec with its kind (`Resolved: source=file:a.md source=dir:docs`), under the same printing rules as a prose resolution.

## `file:<path>`

One file. Its kind is its extension, matched case-insensitively:

| Extension | How it is read |
|---|---|
| `.md`, `.markdown` | file-read tool; copied verbatim |
| `.txt`, `.csv`, `.tsv`, `.json`, `.yaml`, `.yml` | file-read tool; placed inside one fenced block |
| `.xlsx` | the shell tool running the converter shipped with this skill (below); its Markdown output is copied verbatim, followed by the line of the optional sheet render |
| `.pdf` | the file-read tool, page by page, when it can show a PDF; the orchestrator's transcription (below) |
| `.png`, `.jpg`, `.jpeg`, `.gif`, `.webp` | the file-read tool, as an image, when it can show one; the orchestrator's transcription (below) |

Missing file → `ERROR: source file not found at <path>`. Any other extension, or none → `ERROR: source=file:<path>: unsupported file kind (supported: .md .markdown .txt .csv .tsv .json .yaml .yml .xlsx .pdf .png .jpg .jpeg .gif .webp)`.

**`.xlsx` workbooks are read as workbooks**, with nothing converted beforehand. Run, with the shell tool:

```bash
python3 -I "{skill_root}/scripts/xlsx_to_text.py" --max-rows 2000 --max-cols 64 --max-chars 60000 --extract-media "{scratch}/sources/S<n>-media" [--sheet="<name>" ...] -- "<path>"
```

In this command line, and only here, a `~`-prefixed path (`{skill_root}`, or the workbook path as typed) is written as `"$HOME/<the part after ~/>"`, the whole value inside one pair of double quotes (`$HOME` expands inside them, a `~` does not); the command line itself is never written into a prompt, a ticket or a file. The `--` keeps a path that starts with `-` from being read as an option, and the `--sheet=` form does the same for a sheet name that starts with `-`. A `~`-prefixed path read with the file-read tool is passed as typed; when the tool reports it missing, retry once with the home directory expanded, and never record the expanded form. The converter uses only the Python 3 standard library (no package to install) and prints one `## Sheet: <name>` section per worksheet as a Markdown table whose first column is the worksheet row number, so a cell keeps its address. `S<n>` in `--extract-media` is the source id of that workbook. Shared and inline strings, numbers, booleans, cell errors and the cached value of a formula are printed; a number whose cell format is a date format is printed as an ISO date; hidden sheets are included and marked. The structure of the workbook is kept as text, because a workbook used as a document (headings and paragraphs in merged cells, notes, callouts, pasted pictures, struck-through finished items, hidden rows holding old versions; illustrative only) carries meaning outside its cell values: a line break inside a cell, a note or a shape prints as `<br>`; a merged range is not expanded, and its top-left cell carries `[merged c<a>-c<b> rows <x>-<y>]` before its value (the column part left out for a one-column range, the row part for a one-row range); struck-through text prints as `~~text~~`; a hidden row prints its number as `3 (hidden)` and a hidden column its header as `c2 (hidden)`, and their content is still printed. After a sheet's table and its `[truncated: ...]` lines come up to three sections: `### Notes` (one line per cell note or comment, `- c2 row 3 (B3), <author>: <text>`, in row-then-column order), `### Shapes` (one line per text box, callout or other shape, `- "<name>" at c3 row 5 to c6 row 9: <text>`; a chart is listed by name with `(chart; data not read)`, a connector is not listed) and `### Images` (one line per picture, `- "<name>" at c2 row 10 to c5 row 20: <media name> (<bytes> bytes)`). These lines also take the following forms: a note whose author is unknown has no `, <author>` part (`- c2 row 3 (B3): <text>`); a note or shape without text prints `(no text)`; a shape or picture anchored to one cell has no ` to ...` part (`at c3 row 5`), one placed at a fixed position prints `at an absolute position`, and one whose anchor cannot be read `at an unknown position`; a graphic frame that holds no chart prints `- graphic frame "<name>" at ...: (graphic frame; content not read)`; a picture linked from outside the workbook prints `(linked image; not read)`, and one whose image cannot be resolved prints `[unreadable: image ...]` (or another `[unreadable: ...]` reason) in place of its media name. A sheet laid out as a page rather than as a list is printed in the `cells` layout instead of a table: the heading becomes `## Sheet: <name> (layout: cells)` and each non-empty cell gets one line, `- r<row> c<col>[ [merged ...]]: <text>`, with the same hidden markers and caps. The converter's `--layout table|cells|auto` option chooses the layout; the skill always leaves it at `auto`, which picks `cells` for a sheet whose table would be wider than 12 columns and less than 30 percent filled, or that has a merged range of at least 2 rows and 2 columns, and the table otherwise (a user cannot pass converter options). `--extract-media` writes every picture of the sheets read to `{scratch}/sources/S<n>-media/<sheet-slug>-<media name>` (the sheet slug is the sheet name with every character outside `A-Z a-z 0-9 . _ -` replaced by `_`, cut to 40 characters, the media name is the base name of the picture's member (the file name the `### Images` line prints) with the same replacement, and a name already taken by a file written earlier in the run gets `-2`, `-3`, ... before its extension, so two different pictures never share a file and the same picture shown on two sheets whose slugs are equal is written once per sheet; the converter creates the directory only when the workbook has pictures), and the picture's `### Images` line then ends with `, extracted to <file>` (or with `, not extracted (<reason>)` when the file could not be written). That `<file>` path is a run-local location under `{scratch}`: it is read only during the run, and no role copies it into a ticket, a `Sources:` line or a destination; a ticket cites a picture by its sheet and its name. Those files are read-only material for the roles: a role may open one with the file-read tool when that tool can show an image, and a picture whose content no role looked at stays a gap the dossier shows through its `### Images` line; no text is ever recognized from a picture by the converter. A part of the workbook that cannot be read (a missing or malformed note part, drawing, persons part or media member, a relationship whose target points outside the package, or a drawing the sheet declares whose relationship is missing) leaves a one-line `[unreadable: ...]` marker in its sheet section instead of failing the read. `--sheet="<name>"` (one per `?sheet=` value, exact match) restricts the output to those worksheets; without it every worksheet is read. A converter or `curl` message copied into an `ERROR:` line has the home-directory prefix replaced by `~` first (the converter echoes the expanded path it was given). Exit status 2 → `ERROR: source=file:<path> is not a readable .xlsx workbook (<first line of the message>)`, which for an unknown sheet name lists the workbook's sheet names; exit status 3 → `ERROR: source=file:<path> exceeds the workbook safety limits (<first line of the message>)`; any other non-zero status → `ERROR: source=file:<path> could not be converted (<last line of the error output>)`. When `python3` is not on the PATH, try `python` once and use it only if `python --version` reports version 3; otherwise `ERROR: reading an .xlsx source needs Python 3 on the PATH (python3 not found)`. The script is run with `-I` (isolated mode), so nothing in the workbook's directory is imported.

**Sheet rendering (optional).** Text cannot carry the visual arrangement of a sheet used as a page (which callout points at which cell, what a pasted screenshot shows), so a workbook may also be rendered to PDF. After the converter has run and `{scratch}/sources/S<n>.md` is written, when `render=` is not `off` (SKILL.md Argument Parsing; absent means `auto`), run with the shell tool:

```bash
python3 -I "{skill_root}/scripts/xlsx_render.py" --chain <auto|excel|soffice> --only-if-structured "{scratch}/sources/S<n>.md" --out "{scratch}/sources/S<n>-render" [--sheet="<name>" ...] -- "<path>"
```

`--chain` takes the `render=` value. With `auto` the script tests the normalized file itself and renders only a workbook whose converter output holds at least one of `### Shapes`, `### Images`, `(layout: cells)` or a `[merged ` marker (otherwise it prints `Rendered: no (not structured)` and tries nothing); `excel` or `soffice` renders every workbook source with that renderer. Never test the file with a search of your own. The `~` / `$HOME` rule, the `--` and `--sheet=` forms and the `python` fallback are those of the converter's command line above, and `--sheet=` repeats the source's `?sheet=` values. The chain drives a spreadsheet application installed on the host through its automation interface (`osascript` on macOS, the Windows shell interpreter (powershell.exe) on Windows) without showing a window and without saving, or else LibreOffice (`soffice`, headless); it gives the renderer a private copy of the workbook, opened read-only, and writes only under `{scratch}/sources/S<n>-render/`. On a host with neither, the line reads `Rendered: no (...)`. The host's permission prompt for the render command, which launches `osascript`, the Windows shell interpreter or `soffice`, is the user's to approve (SKILL.md Host notes). The script prints exactly one line:

- `Rendered: {scratch}/sources/S<n>-render/<workbook-slug>.pdf (by excel|soffice, <size> bytes, all sheets)`: a PDF of every sheet exists; with `?sheet=` the `excel` renderer renders the first selected sheet only and says `sheet <name>` instead of `all sheets` (plus `; other selected sheets not rendered` when more were selected), while `soffice` always renders every sheet.
- `Rendered: no (not structured)`: `auto` found no page-like structure, and no renderer was tried.
- `Rendered: no (<renderer>: <reason>; ...)`: every renderer tried failed or was skipped (`not installed`, `no spreadsheet application on this platform`, `timed out after 120 s`, `exit status <k>` with the first line of its message, `no PDF produced`, `sheet not found: <name>`).

Append that line as the LAST line of the normalized file's content, after the converter output and after any intake `[truncated: ...]` line (the line itself is never cut), write the file again and compute `Chars:` with the line included, so the dossier shows whether a render exists and by which renderer, or why not. A render that is skipped or fails never stops the run and never prints an `ERROR:`; when the line is `Rendered: no (...)` with renderer reasons (anything but `not structured`), print `WARNING: source S<n> (<origin>): no sheet render (<reasons>)` once and repeat it in the Final summary. A non-zero exit status of the script, or output without a `Rendered:` line, is handled the same way with the line `Rendered: no (render script failed)`. The rendered PDF is run-local, read-only material under `{scratch}`, treated exactly like the extracted pictures: a role may open it with the file-read tool when that tool can show a PDF, its path is never copied into a ticket, a `Sources:` line or a destination, and a render nobody looked at is not a gap (the text dossier is the source of record; the render is an aid).

**`.pdf` and image files are transcribed, not recognized.** A `.pdf` file is shown page by page, and a `.png`, `.jpg`, `.jpeg`, `.gif` or `.webp` file as an image, by the file-read tool when that tool can show the file; the orchestrator then writes into the normalized file what the tool showed: the line `[transcribed from <pdf|image> by the file-read tool; wording and layout may be incomplete]` as the first content line, then one fenced block (info string `text`) holding the transcription: text in reading order, tables as Markdown tables, each figure or screenshot described in one or two lines (what it shows, its visible labels), and for a PDF a line `[page <k>]` before the text of each page. The transcription is the orchestrator's reading of what the tool showed, not an OCR result: no text-recognition engine runs anywhere, and a word the tool did not show is never guessed. A PDF of more than 40 pages is transcribed up to page 40, the fenced block is followed by `[truncated: source S<n> has <k> pages; pages beyond 40 were not read]` and the header says `Truncated: yes` (the 60,000-character cap applies on top). When the file-read tool reports that it cannot show the file (no image or PDF support on this host) → `ERROR: source=file:<path>: this host's file-read tool cannot show a <pdf|image> file` and stop. A ticket's `Sources:` line cites a PDF by its page number (`page 3`) and an image by its file name.

## `dir:<path>`

Every regular file directly inside the directory (subdirectories are not descended, files whose name starts with `.` are skipped), in byte-wise sorted name order, each handled as a `file:` source and numbered in that order. The supported kinds are those of the `file:` table, PDFs and images included, so a directory of screenshots expands into one source per image, each transcribed as above, and the 50-source cap counts every expanded file. A discovered name is checked against the character rule like a typed path; a name that breaks it is skipped and named in the WARNING below (it never reaches a shell command). A file of an unsupported kind, or with a name outside the character rule, is skipped, and every skipped file is named once in `WARNING: source dir:<path> skipped <k> file(s) (unsupported kind or name): <names>`; a subdirectory is counted in `WARNING: source dir:<path> has <k> subdirectories, which were not read`. Missing directory → `ERROR: source directory not found at <path>`; no supported file → `ERROR: source dir:<path> holds no supported file`.

## `mcp:<server>/<tool>[?<name>=<value>&...]`

`<server>` is the name of an MCP server in this session's live tool inventory and `<tool>` names one of its tools exactly (illustrative only: a wiki page getter, an issue reader, a document fetcher).

1. **Find the tool.** No such server → `ERROR: source mcp:<server> is not available in this session`; no such tool → `ERROR: source mcp:<server>/<tool>: no such tool on that server`.
2. **Read-only check.** The tool's name and declared description MUST read as retrieval (get, read, fetch, list, search, export; illustrative only). A tool whose name or description says it creates, updates, deletes, sends, posts, comments or moves anything → `ERROR: source mcp:<server>/<tool> is not a read-only tool` and stop; the property is what the tool does, decided from its description, never from the name alone.
3. **Arguments.** Each `<name>=<value>` pair of the query becomes the parameter `<name>`, converted to the parameter's declared JSON type when its schema declares one (integer, number or boolean; otherwise a string); a value that does not convert → `ERROR: source mcp: parameter <name> expects <type>`. A required parameter with no pair → `ERROR: source mcp:<server>/<tool> needs <name>=<value> in its query`. A `<value>` follows the character rule of SKILL.md Argument Parsing (letters of any script allowed; no double quote, backtick, `$`, backslash or control character) and contains no `&` (the pair separator) or whitespace; the first `=` of a pair separates name and value, later ones belong to the value.
4. **Call once.** The result's text content (every text block, in order; a JSON result pretty-printed) is the source content. An error result → `ERROR: source mcp:<server>/<tool> failed (<first line of the error, at most 200 characters>)`; an empty result → `ERROR: source mcp:<server>/<tool> returned no content`.

### An MCP item named in prose

A prose statement may name an item reachable through an MCP server of the session by its title or by its web URL rather than by the identifier the server's read tool takes (illustrative only: the wiki page titled "Requirements", an issue given by its link). Prose resolution then:

1. **Picks the server and the read tool**: the server the statement names, or else the one server whose tools read that kind of item, and the one tool on it whose name and description read as retrieval of a single item (the read-only check of step 2 above applies). Two candidates or none → ask, as for any ambiguous prose statement.
2. **Passes a URL as is** when the read tool declares a parameter whose description says it takes the item's URL; no lookup is made.
3. **Looks the item up once** otherwise: one call of a tool of the same server whose name and description read as search or listing (the same read-only check applies), with the title or the URL as its query. Exactly one result whose title equals the stated title (case-insensitive, surrounding whitespace ignored) or whose URL equals the stated URL → its identifier fills the read tool's identifier parameter. Zero such results, two or more, no search or listing tool on the server, or an error result → ask the user, listing at most 5 candidates (title and identifier) when there are any; when the ask-user tool is unavailable, denied or erroring → the Prose resolution `ERROR:` (`cannot resolve the request's input or output statement`) and stop, never a guess.
4. **Echoes** the outcome on the `Resolved:` line as the complete `source=mcp:<server>/<tool>?<parameter>=<identifier>` spec. The lookup is part of the resolution, not a source: its result is not written to `{scratch}/sources/`, never reaches the dossier, and at most one lookup call is made per statement.

A URL stated in prose is reached through one access channel (SKILL.md Argument Parsing, **Platform item URLs**): the MCP server the statement names or means (this subsection), the platform's signed-in command-line client (`## cli:<command>`), its HTTP API (`## api:<url>`), the browser tool (`## browser:<url>`), or a plain `GET` of the URL as typed. A page behind a sign-in is usually unreadable by a plain `GET`, which then returns the sign-in page; that attempt counts as failed and the next channel is tried (next subsection), so a statement may, but need not, say which channel to use or name the variable that holds a token.

### A platform item named by URL in prose

A prose input statement may name, by its web URL, an item on a platform (a wiki page, a work item, an issue, a document page; illustrative only). When the statement neither names nor means one channel, Prose resolution (SKILL.md Argument Parsing, **Platform item URLs**) lists the channels that apply on this host in the input candidate order (the MCP server, the signed-in client, the API with a named token variable, the browser, the API with a conventional variable, the API without a token, the plain `GET`) and derives, from the URL and its own knowledge of the platform, what each needs; it may guess (**Best guess**), because every guess is printed before it runs and judged by its outcome:

1. **Through the client**: `source=cli:<command>`, a read-only command of the platform's command-line client that prints the item (a view, get or show form; illustrative only), plus `source_content_path=<jq path>` when it prints JSON and the content sits in one field; a candidate only when the client is on the PATH and its status command says it is signed in (**Auth**).
2. **Through the API**: `source=api:<endpoint>`, the read endpoint whose response carries the item's content (with the query parameter that adds the content when the API leaves it out by default; illustrative only), following the `api:` URL pattern of `## api:<url>` (a character that pattern forbids is percent-encoded, never dropped); `source_content_path=<jq path>` when the response is JSON and the content sits in one field (without it the whole body is the content); and `source_auth_env=<VAR>`, with `source_auth_scheme=bearer|basic`, when the platform requires a token: the variable the statement names or a typed `source_auth_env=`, else a conventional name the orchestrator knows for the platform that the set/unset probe finds set (its name printed on the `Resolved:` line, its value never read).
3. **Through the browser**: `source=browser:<item URL>`, the page's text (`## browser:<url>`); a candidate only when this host has the browser tool.
4. **As typed**: `source=api:<the URL as typed>`, a plain `GET`, the last candidate.

The first candidate's tokens are printed on the `Resolved:` line and its `Derived: input from <item URL without query>: via <channel>, ...` line names the later candidates after `then`, before anything is read. Intake I-2 tries the candidates in that order: a failed attempt (an HTTP status outside 200-299, a body or page that is a sign-in page even with a 2xx status, an empty content, a command that exits non-zero, a tool error) prints `Tried: input <item URL without query> via <channel>: <endpoint without query, or command>: <outcome>` instead of its kind's `ERROR:` line, then the next candidate's own `Derived: input from` line is printed and that candidate runs; the first attempt that succeeds becomes the source, and its normalized file carries `Derived from: <item URL without query>` after its `Origin:` line (not for the plain `GET`, whose origin is that URL already). Every attempt is a read: the read-only rule is unchanged, and at most one request, command or page read is made per candidate (plus a retry after the sign-in question). When every candidate failed, the sign-in rule of SKILL.md Argument Parsing **Auth** applies if at least one failure was a missing sign-in (an HTTP 401 or 403, a sign-in page, a client that says it is not signed in): one ask-user question, then one retry, or, non-interactively, `ERROR: input <item URL without query> needs a sign-in to <host>: sign in with the platform's command-line client or the browser, or re-run with <re-run tokens, with source_auth_env=<VAR> or auth_env=<VAR> to fill in>`; otherwise `ERROR: could not read <item URL without query> (tried: <channel>: <outcome>; ...); sign in to <host> with the platform's command-line client or the browser, or re-run with <re-run tokens>` and stop, where the re-run tokens are the complete token set of every channel tried (Argument Parsing, **Best guess**).

## `api:<url>`

An HTTP `GET` of `<url>` (`http` or `https` only, same pattern as the `api:` destination). The optional `source_auth_env=<VAR>` names an environment variable holding a token, sent as a bearer token unless `source_auth_scheme=basic`; only the name is ever written, and `[ -n "${VAR:-}" ] && echo set || echo unset` (run with the variable's name in place of `VAR`) MUST print `set`, else `ERROR: source api: environment variable <VAR> is not set`; then `case "${VAR:-}" in *\"*|*\\*) echo bad;; *) echo ok;; esac` MUST print `ok` (a value holding a double quote or a backslash cannot be written into the `curl` config), else `ERROR: source api: environment variable <VAR> holds characters the fetch cannot carry`. Fetch with the shell tool (`{scratch}/sources/` exists: Intake I-1 creates it):

```bash
printf 'header = "Authorization: Bearer %s"\n' "$VAR" | curl -sS -g --max-time 120 --connect-timeout 15 -K - \
  -o "{scratch}/sources/S<n>.body" -w '%{http_code}' "<url>"
```

With `source_auth_scheme=basic` the header is `Authorization: Basic <base64 of the variable's value>`, computed inside the same pipeline, so neither the value nor its encoding reaches a command line or a file (`printf` is a shell builtin, and `base64` reads the value from its standard input and is available on macOS and Linux alike):

```bash
printf 'header = "Authorization: Basic %s"\n' "$(printf '%s' "$VAR" | base64 | tr -d '\n')" | curl -sS -g --max-time 120 --connect-timeout 15 -K - \
  -o "{scratch}/sources/S<n>.body" -w '%{http_code}' "<url>"
```

The variable then holds whatever the platform expects before encoding (illustrative only: `user:token`, or `:token` with an empty user name); the skill never prints it or its encoding, and the `[ -n ... ]` and `case` checks above apply unchanged. Without `source_auth_env=`, drop the `printf ... |` prefix and the `-K -` option. A status outside 200-299, or a transport failure → `ERROR: source api:<url without query string> returned HTTP <status>` (or `could not be fetched (<first line of the curl error>)`) and stop. Without `source_content_path=`, the body is read back with the file-read tool and becomes the source content (a JSON body pretty-printed with `jq .` when `jq` is available, otherwise verbatim; any other body verbatim, markup included). With `source_content_path=<path>` (the `id_path=` grammar of the `api:` destination: a `jq` path that starts with a `.name` step and is made only of `.name` and `[index]` steps, matching `^\.[A-Za-z_][A-Za-z0-9_]*(\.[A-Za-z_][A-Za-z0-9_]*|\[[0-9]+\])*$`, else `ERROR: source api: unusable source_content_path <path>`, checked before anything is read; `command -v jq` failing → `ERROR: source api: source_content_path= needs jq on PATH`), the content is the output of `jq -r '<path> // empty' "{scratch}/sources/S<n>.body"`; an empty result, or a body that is not JSON (`jq` exits non-zero), → `ERROR: source api:<url without query string> has no content at <path>` and stop. This also catches a sign-in page returned with a 2xx status, which is not JSON. The response body is never printed.

**A sign-in page is a failed read.** A page behind a sign-in often answers a plain `GET` with a 2xx status and the platform's sign-in page instead of the item (a login form, a redirect-to-sign-in notice; illustrative only). After a 2xx read without `source_content_path=`, the orchestrator reads the body back and judges whether it is such a page; when it is, the attempt counts as failed, exactly like a status outside 200-299: a typed `source=api:` stops with `ERROR: source api:<url without query string> returned a sign-in page, not the content; sign in with the platform's command-line client or the browser, or re-run with source_auth_env=<VAR>`, and an attempt of a source derived from a platform item URL prints its `Tried:` line (outcome `sign-in page`) and the next channel is tried, or the sign-in rule applies when none is left (`### A platform item named by URL in prose`). The same holds for every other failure of this section: a typed `api:` source stops with its `ERROR:` line, a derived attempt becomes a `Tried:` line.

## `cli:<command>`

One run of a command of a command-line client installed on the host (illustrative only: a work-item platform's client printing one item), with the shell tool; its standard output is the source content. The command is written in a double-quoted token, `source="cli:<command>"`, or stated in prose, and is printed on the `Resolved:` line in that form.

- **Read-only.** A derived command (Prose resolution) is one the orchestrator knows only reads (a view, get, list or show form of the client; illustrative only). A typed command is the user's own: it runs as given, after it has been printed in full, through the host's permission prompt, which is the user's gate for it (SKILL.md Host notes).
- **Command text.** The `cli:` exemption of the SKILL.md **Character rule**: `$` only in a `$NAME` or `${NAME}` variable reference, expanded by the shell, never by the skill, and never printed as a value; no control character and no newline (else `ERROR: source=<spec without query> contains characters this skill does not accept`); never a literal token value (else `ERROR: source cli: a credential in the command line; use $VAR`). Both are checked before anything runs.
- **On the PATH.** The command's first word must be found by `command -v "<first word>"`, else `ERROR: source cli: <first word> is not on PATH`.
- **Run once.** Run `<command> >"{scratch}/sources/S<n>.body" 2>"{scratch}/sources/S<n>.err"` with the shell tool (`{scratch}/sources/` exists: Intake I-1 creates it). Exit status non-zero → `ERROR: source cli:<command> failed (exit <n>: <first line of the error output, at most 200 characters>)`; an empty output → `ERROR: source cli:<command> returned no content`. The output is read back with the file-read tool: JSON is pretty-printed with `jq .` when `jq` is available; with `source_content_path=<path>` (the grammar and checks of `## api:<url>`), the content is the output of `jq -r '<path> // empty' "{scratch}/sources/S<n>.body"`, and an empty result or output that is not JSON → `ERROR: source cli:<command> has no content at <path>`. The output is never printed to the terminal.
- **Derived attempts.** A command derived from a platform item URL turns every failure above into a `Tried:` line and the next channel (`### A platform item named by URL in prose`); output that says the client is not signed in counts as a missing sign-in.

`{parent-slug}` from a `cli:` source is the command's first word (Intake I-5).

## `browser:<url>`

The text of one page, read through the **browser tool** of this session (SKILL.md Host notes: a tool that navigates to a URL, reads the page's text, fills a field and clicks; present only when the session has one, never required). `<url>` follows the `api:` URL pattern of `## api:<url>` and is printed without its query string. On a host with no browser tool → `ERROR: this host offers no browser tool; pass source=api:<url> or source=cli:<command>`.

1. **Open.** Open `<url>` in the browser tool. A navigation error → `ERROR: source browser:<url without query string> could not be read (<first line of the error, at most 200 characters>)`.
2. **Judge the page.** A sign-in page (judged by the orchestrator from the page: a login form, a redirect-to-sign-in notice; illustrative only) is a missing sign-in: the sign-in rule of SKILL.md Argument Parsing **Auth** applies (one question, then one retry; non-interactively the `needs a sign-in` `ERROR:`), and a source derived from a platform item URL first prints its `Tried:` line and tries the next channel.
3. **Read.** The content is the page's text as the browser tool reads it (its text or accessibility read, never a transcription of a screenshot), placed inside one fenced block. An empty page → `ERROR: source browser:<url without query string> returned no content`. Nothing on the page is clicked, filled or submitted: the read-only rule holds for the browser as for every source.

`{parent-slug}` from a `browser:` source is the URL's last non-empty path segment, else its host (Intake I-5).

## Locators and excerpts

A locator names lines of a normalized file: `S<n>:L<a>-L<b>` (a line range, inclusive), `S<n>:L<a>` (one line) or `S<n>` (the whole source). Line 1 is the `Source:` line of that file. The decomposer emits locators in two places of its `## Result`: `**Partition basis**:` and each ticket's `source_refs:` sub-line.

**Excerpt extraction** (orchestrator, before each planner spawn, initial and retry): for each locator of the ticket's `source_refs`, copy the source's header block once (lines 1-6, or lines 1-7 for a source with a `Derived from:` line), then the named lines; when a named line is a row of a Markdown table, also copy once the nearest `## Sheet:` heading above it (a workbook source), that table's header row and separator row, and the table's first data row (in a workbook, worksheet row 1, which usually names the columns). When a named line is a line of a `### Notes`, `### Shapes` or `### Images` section, or a cell line of a sheet in the `cells` layout, also copy once the nearest `## Sheet:` heading above it. When a named line lies in a source that has a `[transcribed ...]` line or a `Rendered:` line, also copy that line once. Put the result under `## Source excerpts` in the planner spawn prompt, each excerpt introduced by its locator and origin. Cap: 8,000 characters per ticket, cut at a line boundary with the line `[truncated: source excerpts exceed 8000 characters]`. The whole dossier is never inlined into a planner spawn.

The planner ends the ticket's `### Background` with one line `Sources: <locator> (<origin>[, <where in it>]); ...` naming every excerpt it drew on (for a spreadsheet, the sheet and row numbers of the table rows, or the sheet and name of a note, shape or picture; for a document, its heading; for a PDF, its page (`page 3`); for an image, its file name), so an acceptance criterion that restates a requirement of a source can be traced to it. Every requirement drawn from a source is restated in the AC text itself (the value, the behaviour, the limit); an AC never points at a locator, because the ticket-evaluator sees no source. A ticket that used no excerpt writes no `Sources:` line. The `, extracted to <file>` path at the end of an `### Images` line is a run-local `{scratch}` location: the planner never copies it into a ticket (its `Sources:` line included) and cites the picture by its sheet and name instead.

## Partition basis

The decomposer decides it; the rule lives in `references/spec-decomposer-input.md` (`## Source dossier`) and `references/agents/decomposer.md` (`## Source dossier handling`). In short: a source, or one part of it (a sheet, a section, a list), is **partition-authoritative** when it enumerates two or more discrete items that each state their own scope and outcome as work still to be done; a list of attributes of one deliverable, a glossary, a status table of finished work or a free-form narrative is context. With `findings=` the partition basis is always the findings units; with `brief=` it is always derived from the brief; otherwise the decomposer reports `**Partition basis**: <locator>` or `derived`, and the Final summary repeats it.

## Final summary

When `source=` was given, the Final summary (`references/write-path-templates.md`) carries one `Sources:` line per source after the `Destination:` line and its `Derived from:` and `Parent:` lines when present (after the `Created:` line and those same lines in the failure block): `Sources: S<n> <kind> <origin> (<chars> chars[, truncated])`, followed by `Partition basis: <locator> | derived | findings | brief`, and repeats every intake `WARNING:` line, the `no sheet render` warning included; a workbook's `Rendered:` line itself stays in the dossier and is not repeated.
