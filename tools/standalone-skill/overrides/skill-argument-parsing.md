## Argument Parsing

This host passes no argument variable: the input is the user's request text, that is, the text of the message that invoked this skill (everything after `/create-ticket` when it was typed as a command). Parse it into one mode: `findings=<path>` (scan `findings=`); `brief=<path>` (scan `brief=`); else bare-description free-text. `source=<spec>` tokens (below) add inputs to any mode and may stand alone: a request made only of tokens with at least one `source=` is a bare-description run whose description Intake derives.

**Prose resolution**: the request may state its input and its output in prose, in any language, after the skill name (a statement naming material to read: a file, a directory, a workbook and a sheet of it, an item or page reachable through an MCP server of this session, a URL; or a statement naming where the tickets go: a directory, a platform reachable through an MCP server, an item there to attach them to, an endpoint). After the token scan (so every explicit token is known) and before any token is acted on, translate every such statement into the equivalent `source=`, `brief=`, `findings=`, `destination=`, `parent=` or `?sheet=` form by what the statement names, never by the wording of one language. Rules: an explicit token wins over a prose statement about the same thing; prose never sets `confirm=`, `depth=`, `render=`, `rounds=`, `max_tickets=`, `keep_scratch=` or `constraint_<key>=off`; a resolved value passes the same character rule and checks as a typed token; an item reachable through an MCP server that the statement names by title or URL instead of by identifier is looked up as `references/sources.md` `### An MCP item named in prose` defines (one read-only search call per candidate server; an input statement reads each exact match when there are one to three, from one to three candidate servers, an output statement needs exactly one server and one match, and anything else is asked about), and a URL resolves as **Platform item URLs** below defines (through one access channel: an MCP server of this session, the platform's signed-in command-line client, its HTTP API, the browser tool, or a plain `GET` of the URL as typed); print one line `Resolved: <the tokens, an api: URL without its query string>` as the run's first output, after any question the resolution asked, so the reading is visible before anything runs (omit the line when nothing was resolved, inferred or normalized); an output statement that resolves two ways (two servers, two directories of that name) and any statement that resolves to nothing (a name that matches no file, no server, no tool) → ask the user with the ask-user tool; when it is unavailable, denied or erroring, `ERROR: cannot resolve the request's input or output statement: <statement>` and stop, never an assumption, because a wrong destination cannot be undone remotely. An input statement that resolves two or three ways (two files of that name; illustrative only) is read every way instead of being asked about, because reading is read-only: each candidate becomes its own `source=` spec, all of them printed on the `Resolved:` line; four or more candidates are asked about like an output. A Markdown file named by a prose input statement becomes `brief=` when the statement calls it a brief or its frontmatter (opened with the file-read tool) carries `slug`, `findings=` when the statement calls it findings or its frontmatter carries `findings_version`, and `source=file:` otherwise; any other file kind is always `source=file:`. The description is the request text with the resolved input and output statements removed (a resolved value never reaches `{parent-slug}` derivation); when nothing remains, the request counts as made of tokens only (Intake I-5 derives `{intent}`). A resolved value that contains whitespace, `?` or `&` is printed on the `Resolved:` line in double-quoted token form (`source="file:My Docs/a.xlsx?sheet=Open items"`, `source="cli:<command>"`); the line shows the reading, the run acts on the resolved values themselves and never re-parses the line, so a sheet name that token form could not carry is still passed to the converter whole. When the request holds a prose input or output statement, or a kind-less URL (a `source=` or `destination=` value without a kind), the `Resolved:` line is mandatory output and Phase 1 must not start before it is printed; a derived destination's body template is written only to `{scratch}/template-derived.json` (no other file name).

**Platform item URLs**: a URL named by a prose statement (an input: material to read; an output: where the tickets go, or the item to create them under or as children of), and an `http://` or `https://` URL typed as a `source=` or `destination=` value without a kind prefix, which is resolved exactly like an input or an output statement naming that URL (a typed `source=api:<url>` stays one verbatim `GET`, and a typed `destination=api:<url>` is the `api:` adapter as written), is reached through one **access channel**, chosen by the orchestrator from the URL, the statement and its own knowledge of the platform, never by the wording of one language:

| Channel | Token | Reads | Creates |
|---|---|---|---|
| an MCP server of this session that reaches the platform | `mcp:` | the MCP rules above | the `mcp:` adapter of `references/destinations.md` |
| the platform's own command-line client, on the PATH and signed in | `cli:<command>` | one read-only command (`references/sources.md` `## cli:<command>`) | one create command per ticket (`references/destinations.md` `## cli:<command template>`) |
| the platform's HTTP API, with a token variable when it needs one | `api:<url>` | one `GET` of a read endpoint | one `POST` per ticket to a create endpoint |
| the **browser tool** of this session (Host notes), whose browser session may already be signed in | `browser:<url>` | the page's text | the create form, filled and submitted once per ticket |
| a plain `GET` of the URL as typed (an input only) | `api:<url>` | the body as served | none |

When the statement names a channel (says to read or deliver through an MCP server, the command-line client, the API or the browser, or names one of them), only that channel is used and the MCP rules above apply to an MCP server. When the request names a token variable (**Auth** (1) below), the API channel with that variable is the only candidate for the direction it serves. Otherwise the orchestrator tries the channels that apply, in this **candidate order**: for an input, the MCP server, the signed-in client, the browser, the API with a conventional variable (**Auth** below), the API without a token when the platform serves that item without one, and last the plain `GET`; for an output, the MCP server, the signed-in client, the API with a conventional variable, and last the browser, because a form-driven create is fragile. A channel applies only when this host has it (a client on the PATH, the browser tool present, a server in the session). The orchestrator may move a channel by its judgment of fit and then says why on the `Derived:` line: a kind of page the platform's API does not expose goes to the client or the browser; a signed-in client beats a token the user would first have to name; the browser is the only channel that reuses a browser sign-in. An explicit token always wins (**Precedence**).

- **Best guess**: the orchestrator may guess every derived value (an endpoint, a command, a content field, a body shape, a parent link, a form) from its knowledge of the platform; it need not be certain, because every guess is printed before it runs and its outcome decides. For an input, the candidates are tried in order where the source is read (Intake I-2): a failed attempt, which is an HTTP status outside 200-299, a body or page that is a sign-in page even with a 2xx status (a login form, a redirect-to-sign-in notice; illustrative only, judged by the orchestrator from the body), an empty content, a command that exits non-zero or a tool error, prints `Tried: input <item URL without query> via <channel>: <endpoint without query, or command>: <outcome>`, and the next candidate is tried after its own `Derived: input from` line; the first attempt that succeeds is the source. For an output, the guess is verified before anything is created by a **read probe** in the destination preflight: with the same channel and credentials, read the parent item (without a parent, the container the URL names): for `api:` one `GET` of its read endpoint that returns a 2xx status and a JSON body that is not a sign-in page, for `cli:` one read-only command of the client for it that exits 0, for `browser:` the create form opened from the URL with a title and a body field, for `mcp:` one call of a read-only tool of the server that reads that item; a passing probe prints `Probe: output <item URL without query> via <channel>: <what was read>: ok`, a failing one prints a `Tried: output ...` line and the next candidate is derived (its own `Derived: output from` line) and probed. A failure before any create (a probe, a sign-in) may fall through to the next channel; once a create has been attempted, nothing falls through, because the item may exist (the remote-failure rule of `references/destinations.md`). Every candidate failed: when at least one failure was a missing sign-in, the sign-in rule of **Auth**; otherwise, for an input, `ERROR: could not read <item URL without query> (tried: <channel>: <outcome>; ...); sign in to <host> with the platform's command-line client or the browser, or re-run with <re-run tokens>`, and for an output, `ERROR: output <item URL without query>: the derived <channel> could not reach the parent item (<outcome>); nothing created; pass <re-run tokens>` (the last channel tried; the earlier ones are on their `Tried:` lines), and stop. The **re-run tokens** are the complete token set of every channel tried, filled with its derived values, a variable left as `<VAR>` to fill in, one set per channel joined by ` or ` (illustrative only: `source=api:<url> source_content_path=<jq path> source_auth_env=<VAR> or source="cli:<command>" or source=browser:<url>`), so the line can be copied and completed in a run that cannot ask. When several URLs failed, the line carries one complete set per URL; because a typed `source_content_path=`, `source_auth_env=` or `source_auth_scheme=` applies to every source of a run (**Precedence**), an `ERROR:` whose URLs need different values of one of them ends with `; run one platform per request`.
- **Derived input** (the statement names an item URL as material to read): through the API, `source=api:<read endpoint>`, a request whose response carries the item's content, plus a content path (`source_content_path=<jq path>`) when the response is JSON and the content sits in one field, plus a token variable and its scheme (`source_auth_env=<VAR>` / `source_auth_scheme=<scheme>`) when the platform requires a token (**Auth** below); through the client, `source=cli:<command>`, a command the orchestrator knows reads that item (a view, get or show form; illustrative only), plus a content path when it prints JSON and the content sits in one field; through the browser, `source=browser:<item URL>`, the page's text; as a plain `GET`, `source=api:<the URL as typed>`. A content path, token variable or scheme derived for a source belongs to that source only: the `Resolved:` line prints it next to its source, in the form `source=api:<url> (content <jq path>, token variable <VAR> (<scheme>))` (each part only when derived), and it never applies to another source of the run; a typed `source_content_path=`, `source_auth_env=` or `source_auth_scheme=` token stays run-wide and wins for every `api:` and `cli:` source (**Precedence**). `references/sources.md` `### A platform item named by URL in prose` holds the rest.
- **Follow-up reads**: for a source derived from a platform item URL (in prose or typed without a kind), when the statement asks for the item's child pages or sub-items, or the first response says it is one page of several, the orchestrator may make up to 20 further read-only requests through the SAME channel and host, each printed on its own `Derived: input from <item URL without query>: ...` line before it runs. Each further item becomes its own source, numbered after every source of the request in the order read, with `Derived from:` naming the URL the user gave; a failed follow-up prints a `Tried:` line and is skipped with `WARNING: follow-up read of <item URL without query> via <channel> failed (<outcome>); skipped` (repeated in the Final summary), never an `ERROR:`. Follow-up reads stop when the run holds 50 sources, with `WARNING: follow-up reads of <item URL without query> stopped at the 50-source cap` (repeated in the Final summary); they never raise the 50-source `ERROR:`, which counts only the specs the request carries (`references/sources.md` **Count**). The read-only rule and the other caps of `references/sources.md` are unchanged.
- **Derived output** (the statement names an item URL as where the tickets go, or as the item they are created under or as children of): through the API, `destination=api:<create endpoint>`, an endpoint that creates one item per `POST`; `template=<path>` where `<path>` is `{scratch}/template-derived.json`, a JSON request body the orchestrator writes with the file-write tool, holding `{title}` and `{body}` as whole string values and, when the statement named an item to create under, `{parent}` where the platform's API expects the parent link (`{parent}` may sit inside a longer string, such as a link URL that embeds the identifier; `references/destinations.md` `## api:<url>`); `id_path=<jq path>`; `parent=<id>`, the item's identifier taken from the URL, when the statement creates under it; `content_type=<media type>` when the endpoint needs a body media type other than `application/json`; `auth_env=<VAR>` / `auth_scheme=<scheme>` as below. Through the client, `destination=cli:<command template>`, a create command of the client holding `{title_file}`, `{body_file}` or `{request_file}` and, with a parent, `{parent}` (`references/destinations.md` `## cli:<command template>`), plus `id_path=` when it prints JSON and `template=` as above when it takes a JSON file. Through the browser, `destination=browser:<item URL>`, with `parent=<id>` taken from the URL when the URL is the item to create under. Through an MCP server, `destination=mcp:<server>/<tool>`, the server's create tool (`references/destinations.md` `## mcp:<server>[/<tool>]`), with `parent=<id>` taken from the URL when the statement creates under it and, as a best guess, `mcp_<name>=<value>` for the create tool's other parameters (a project or container key the URL shows; illustrative only), printed on the `Resolved:` and `Derived:` lines, shown in the confirmation question and verified by the read probe of the parent item; a typed `mcp:` destination never gets a guessed value. A typed `mcp_<name>=<value>` token is also accepted with a destination URL typed without a kind or named in a prose output statement: when the MCP channel delivers, it wins over a guessed value for that parameter; when another channel delivers, print `WARNING: mcp_<name>= ignored (the destination is reached via <channel>)` once that channel's read probe has passed (repeated in the Final summary). A kind of item the statement names (as tasks, as issues, as sub-items; illustrative only) is carried into the derived endpoint, command, body or form as that platform expects; a statement naming none gets the platform's default kind, said on the `Derived:` line. For a derived output only, `{scratch}` is created right after the `Resolved:` and `Derived:` lines are printed (only read-only calls (the resolution's own lookups and file checks, and the sign-in probes of **Auth**) run before the `Resolved:` line; nothing is written before it, nor before the `Derived:` lines), by the two commands and the `.gitignore` step of the scratch paragraph at the end of this section (its `ERROR:` included), and a derived template is written into it at once, before the non-interactive sign-in check of **Auth** and before the destination preflight; the scratch paragraph then reuses that `{scratch}` instead of creating a second one, and the destination preflight, which runs after it and holds the read probe, finds the file. Because the directory does not exist yet when the `Resolved:` and `Derived:` lines are printed, those two lines show the template as the literal `{scratch}/template-derived.json`; every later line that names it (the `needs a sign-in` `ERROR:` of **Auth**, the `Derived: output from` line of a later candidate, and the confirmation question of `references/destinations.md` and its `ERROR:`) prints the real path, `{scratch}` replaced by the recorded directory. A later candidate channel, tried after a failed read probe, that needs a body template of its own (a command-line client that takes a JSON file, tried after the API; illustrative only) gets `{scratch}/template-derived.json` rewritten, its whole content replaced with the file-edit tool (as for the `local:` counter), before its probe runs, and its own `Derived: output from` line names that file; the destination preflight writes nothing outside `{scratch}`.
- **Derived URL rule**: a derived endpoint follows the `api:` URL rules of `references/destinations.md` (preflight steps 2 and 3: no whitespace, quote, backtick, `$`, backslash, `[`, `]`, `{` or `}`, and no credential in the URL); a path or query character those rules forbid is percent-encoded in the derived URL (a space as `%20`, `{` and `}` as `%7B` and `%7D`; illustrative only), never dropped. Query parameters, such as an API version parameter, are allowed. The scheme rule of preflight step 2 (`https://`, plain `http://` only for a loopback host) binds an output only, its create endpoint and the read endpoint of its probe: the read endpoint derived for a source, like every `api:` and `browser:` source URL, may be `http://` or `https://` for any host, and a token is never sent to a non-loopback `http://` URL (`references/sources.md` `## api:<url>`). A derived command follows the `cli:` rules of the **Character rule** below and never carries a token value.
- **Auth**: what is at hand is looked for in this order. (1) A token variable the request names: a `$NAME`, or an identifier the statement calls a token, variable, secret or credential, or a typed `source_auth_env=` / `auth_env=` token; it forces the API channel, which with that variable is then the only candidate (**candidate order** above), and it becomes `source_auth_env=` when the statement is about reading, `auth_env=` when it is about delivering, and both when it says so or when both derived endpoints are on the same host; a variable named in prose for one input URL belongs to that source only, like every derived value (**Derived input**), while a typed `source_auth_env=` token is run-wide (**Precedence**). (2) A signed-in command-line client: its first word is on the PATH (`command -v`) and one read-only status command the orchestrator knows for that client (a who-am-I or auth-status form; illustrative only), printed before it runs, exits 0; its output may name an account and is shown on the terminal only, one line at most, and never written into the dossier, a ticket, the Final summary or a spawn prompt. (3) A signed-in browser: the browser tool is present; whether its session is signed in shows only when the page opens. (4) Conventional variable names: the orchestrator may try names it knows for the platform, each checked only with the shell tool running `[ -n "${VAR:-}" ] && echo set || echo unset` (the name in place of `VAR`); it never reads a value and never prints one, a name that prints `unset` is skipped, the first name that prints `set` is used, and the name it uses is always printed on the `Resolved:` line. A variable name matches `^[A-Za-z_][A-Za-z0-9_]*$` like a typed one. The scheme (`bearer` by default, or `basic`) comes from the orchestrator's knowledge of the platform or from the statement. **Sign-in rule**: when a channel needs a sign-in and none of the above is at hand (known before anything is tried, or shown by an outcome: an HTTP 401 or 403, a sign-in page, a client that says it is not signed in): interactive → one question with the ask-user tool, "Sign in to <host> in the browser or with the command-line client (`<login command>`), or set a token variable and give its name; answer done or the name" (naming only the browser or client this host has), then one retry: `done` → the channel that needed the sign-in, a name matching the pattern → the API channel with that variable (printed on a new `Derived:` line before it runs); a retry that fails → the `could not read` or `could not reach the parent item` `ERROR:` above, and an answer that is neither → the error below. Non-interactive (the ask-user tool unavailable, denied or erroring) → `ERROR: <input|output> <item URL without query> needs a sign-in to <host>: sign in with the platform's command-line client or the browser, or re-run with <re-run tokens, with source_auth_env=<VAR> or auth_env=<VAR> to fill in>` and stop. A question asked before anything is tried comes before the `Resolved:` line, so an answered name is printed on it; the error, when known before anything is tried, comes after the `Resolved:` and `Derived:` lines (and, for an output, after the derived template is written, so the re-run line names a file that exists) and before Intake and any preflight, and otherwise where the failure showed (Intake I-2 for an input, the destination preflight for an output).
- **Visibility**: the `Resolved:` line lists every derived token (`source=api:...`, `source="cli:..."`, `source=browser:...`, each followed by the content path, token variable and scheme derived for it in the `(content <jq path>, token variable <VAR> (<scheme>))` form of **Derived input**, `destination=api:...`, `destination="cli:..."`, `destination=browser:...`, `destination=mcp:...`, `mcp_<name>=...`, `template=...`, `id_path=...`, `parent=...`, `content_type=...`, `auth_env=...`, `auth_scheme=...`), each URL without its query string, each variable by its NAME only and a derived template as the literal `{scratch}/template-derived.json` (**Derived output** above). Directly after it, print one line per derived direction: `Derived: input from <item URL without query>: via <channel>, <endpoint without query | command | page>, content <jq path | whole body | page text>[, token variable <VAR> (<scheme>) | , signed-in client | , browser session][, chosen because <reason>][; then <channel>, <channel>]` and `Derived: output from <item URL without query>: via <channel>, <create endpoint without query | command template | form page | create tool>, kind <kind>, parent <id>[, mcp_<name>=<value> ...][, body template {scratch}/template-derived.json][, content type <media type>][, token variable <VAR> (<scheme>) | , signed-in client | , browser session][, chosen because <reason>][; then <channel>, <channel>]` (no `parent` clause when no `parent=` was derived; `then` lists the later candidates in order). Both lines are printed before Intake and before any preflight; a later candidate's `Derived:` line is printed before that candidate runs, and the `Tried:` and `Probe:` lines of **Best guess** are printed as the attempts happen.
- **Precedence**: an explicit token wins over a derived value for the same thing: a typed `template=` replaces the derived template (nothing is written to `{scratch}/template-derived.json`), a typed `mcp_<name>=` replaces the guessed value of that parameter when the MCP channel delivers (else its `ignored` `WARNING:`, **Derived output**), a typed `source=` or `destination=` value that carries its kind is used as typed and nothing is derived for it (a kind-less `http://` or `https://` value is derived like a prose statement), a typed `source_content_path=`, `source_auth_env=` or `source_auth_scheme=` applies run-wide and replaces the value derived for each `api:` (and, for the content path, `cli:`) source, and a typed `source_auth_env=` / `auth_env=` forces the API channel as the only candidate. Prose, derived or not, never sets `confirm=`, `depth=`, `render=`, `rounds=`, `max_tickets=`, `keep_scratch=` or `constraint_<key>=off`.

**Character rule** (every path, directory, sheet name and identifier the request carries, typed or resolved): no double quote, backtick, `$`, backslash or control character; letters of any script are allowed; whitespace only inside a double-quoted token (`source="file:My Docs/a.xlsx"`, the quotes are not part of the value) or in a value resolved from prose. In a path value every backslash is read as `/` before the rule runs, and the normalized path is echoed on the `Resolved:` line and is the path every later line uses (Host notes, **`~` paths**), so a path written with backslashes works; a backslash stays refused everywhere else (identifiers, sheet names, URLs, MCP values). `brief=`, `findings=`, `destination=local:` and `template=` are path values, so their check reads the backslashes first. A `source=` value may carry several specs of several kinds (`references/sources.md` `## Writing a source`), so it is checked twice: the whole-value check before the list split tolerates a backslash, because the kinds are not known yet; after the list split and the kind inference, the per-spec check decides: in a `file:` or `dir:` spec every backslash is read as `/`, and in any other kind it stays refused (a `cli:` command keeps its own exemption below). A value that breaks the rule → the `contains characters this skill does not accept` error of its token (for `destination=local:` and `template=`, the `is not a usable` error of `references/destinations.md`). URLs and environment-variable names keep their own stricter patterns. A `cli:` command (a source or a destination template, typed or derived) is exempt, with three limits: `$` appears only in a `$NAME` or `${NAME}` variable reference, which the shell expands and the skill never expands or prints; no control character and no newline (else `ERROR: source=<spec without query> contains characters this skill does not accept` for a source, `ERROR: destination cli: unusable command template (<rule>)` for a destination); and no literal token value (a string the orchestrator recognizes as a credential, such as a long random-looking secret after a token or password option; illustrative only) → `ERROR: source cli: a credential in the command line; use $VAR` (a source) or `ERROR: destination cli: a credential in the command line; use $VAR` (a destination). A typed command holds whitespace, so it is written in a double-quoted token (`source="cli:<command>"`) and then holds no double quote of its own; a command that needs one is stated in prose.

**Mutual exclusion**: BOTH `brief=` AND `findings=` → print `ERROR: brief= and findings= are mutually exclusive. Pass exactly one.` and stop. Do NOT read either file. Do NOT touch the destination. Do NOT create directories. (Exact wording required: the literal `mutually exclusive`.)

**Input paths**: a `brief=` or `findings=` path may be absolute (it is the user's own file) and follows the character rule above; else print `ERROR: <token>= path contains characters this skill does not accept` and stop. Then check that the file exists with the file-read tool, never with a shell test, before the destination preflight; this is the one existence check of the file (Steps F-1 and B-1 name its output and do not repeat it), and a `~`-prefixed path gets the file-tool retry of Host notes (**`~` paths**) before it counts as missing: a missing findings file → `ERROR: Findings file not found at <path>`, a missing brief → `ERROR: Brief file not found at <path>`, and stop. Error lines and the Final summary echo the path exactly as the user typed it (with backslashes read as `/`; Host notes).

**Option tokens**: scan the same text for these tokens (each runs to the next whitespace, so in a language written without word spaces put a space after the value) and remove them before the bare-description text is used:

- `destination=<spec>`: where Delivery puts the tickets, exactly one destination per run (`## Delivery`, **One destination**). Absent, and no output statement in the request → `local:.local/tickets`; an output statement that cannot be resolved or reached stops with its `ERROR:` line and never falls back to this default. The five kinds, `local:<dir>`, `mcp:<server>[/<tool>]`, `api:<url>`, `browser:<url>` (the create form of a platform item page, filled through the browser tool) and `cli:<command template>` (one create command of a command-line client per ticket, written in a double-quoted token because it holds spaces), and every check on them are defined in [references/destinations.md](references/destinations.md). An `http://` or `https://` URL without a kind prefix (`destination=https://...`) is not an unknown kind: it is resolved exactly like a URL named in a prose output statement (**Platform item URLs** above: derived output, read probe, confirmation), while `destination=api:<url>` is the `api:` adapter as typed.
- `auth_env=<VAR>`, `template=<path>`, `id_path=<path>`: options of an `api:` or `cli:` destination only.
- `content_type=<media type>`, `auth_scheme=bearer|basic`: options of an `api:` destination only (the request body's media type, default `application/json`; how the `auth_env=` token is sent, default `bearer`).
- `mcp_<name>=<value>`: the value of a parameter `<name>`, required or optional, of an `mcp:` destination's create tool (e.g. a project key; illustrative only); also accepted with a destination URL typed without a kind or named in prose, where it counts only when the MCP channel delivers (**Derived output** above).
- `source=<spec>` (repeatable): an input to read before Phase 1. The six kinds, `file:<path>` (a document, an `.xlsx` workbook read as a workbook, or a `.pdf` or image file transcribed through the file-read tool), `dir:<path>` (every supported or text file of a directory tree, down to 5 levels; deeper directories are reported with `WARNING: source dir:<path> has <k> directories below 5 levels, which were not read`, and files beyond the 50-source cap are skipped with `WARNING: source dir:<path> skipped <k> file(s) beyond the 50-source cap`), `mcp:<server>/<tool>[?<name>=<value>...]` (one call of a read-only MCP tool), `api:<url>` (one HTTP `GET`), `cli:<command>` (one run of a read-only command of a command-line client, written in a double-quoted token because it holds spaces) and `browser:<url>` (the page's text, read through the browser tool), their patterns, caps and `ERROR:` lines are defined in [references/sources.md](references/sources.md); the sequence is `## Intake`. One token may carry a comma-separated list of specs and a spec may omit its kind (an `http://` or `https://` URL is resolved like a URL named in a prose input statement, **Platform item URLs** above, while `source=api:<url>` with its kind stays one verbatim `GET`; an existing directory is `dir:`, any other path `file:`; `mcp:`, `cli:` and `browser:` are never inferred from a path or a name); both are resolved as `references/sources.md` `## Writing a source` defines, and the resolved specs are echoed on the `Resolved:` line.
- `source_auth_env=<VAR>`: an environment variable holding a token, for an `api:` source only (distinct from the destination's `auth_env=`; sent as a bearer token unless `source_auth_scheme=basic`); typed, it applies to every `api:` source of the run and wins over a token variable derived for one.
- `source_content_path=<jq path>`: an option of an `api:` or `cli:` source (the field of a JSON response, or of a command's JSON output, that holds the content); typed, it applies to every `api:` and `cli:` source of the run and wins over a content path derived for one.
- `source_auth_scheme=bearer|basic`: an option of an `api:` source only (how the `source_auth_env=` token is sent, default `bearer`); like `source_auth_env=`, typed, it applies to every `api:` source of the run and wins over a scheme derived for one.
- `parent=<id>`: an existing item of an `mcp:`, `api:`, `browser:` or `cli:` destination that every delivered ticket is linked to as its child (the parent is never modified); `<id>` follows the character rule above and contains no whitespace. How the link is set is defined per kind in [references/destinations.md](references/destinations.md).
- `confirm=yes|no`: `confirm=yes` skips the one confirmation question asked before the first `mcp:` / `api:` / `browser:` / `cli:` create, and answers "proceed" at the exhausted-retry question of Phase 4 without asking it (a ticket still graded FAIL after its last round, `rounds=`, is then delivered with the verdict `FAIL (unresolved)`, its remaining issues printed), for every destination kind, `local:` included. **Implied confirmation**: when the tool-role resolution of Host notes found no tool for the ask-user role on this host and the request carries no `confirm=` token, `confirm=yes` is implied: the confirmation before the first remote create is skipped and a ticket still graded FAIL after its last round is delivered as `FAIL (unresolved)`, exactly as with the token typed; right after the destination preflight the run prints once `NOTE: this host has no ask-user tool; running as if confirm=yes was passed (a remote create is not confirmed first, and a ticket still graded FAIL is delivered as FAIL (unresolved)); pass confirm=no to stop instead`, and the Final summary repeats that line. `confirm=no` never implies and never skips: on a host with the ask-user tool the questions are asked as when the token is absent; on a host with no ask-user tool a remote destination stops at the destination preflight with `ERROR: remote delivery needs an interactive confirmation; re-run with confirm=yes to skip it` (for a derived destination followed by ` (derived: <the derived tokens>)`), and a ticket still graded FAIL after its last round stops the run with `ERROR: cannot resolve FAIL gates non-interactively; re-run interactively, or with confirm=yes to deliver as FAIL (unresolved) (draft saved under {scratch})`. Only a missing ask-user tool implies `confirm=yes`: an ask-user tool that exists but errors, or a run where asking is treated as deny, keeps those two `ERROR:` lines, so there the typed `confirm=yes` is what delivers remotely without the question and delivers a ticket still graded FAIL. Nothing else is implied: an ambiguous output statement, a statement that resolves to nothing, a missing sign-in and a typed `mcp:` destination's missing required parameter still stop with their `ERROR:` lines on a host that cannot ask.
- `keep_scratch=yes|no`: whether the run scratch directory `{scratch}` is kept after a clean run. Absent → `no`: the last step of the run removes it when the run ended cleanly, by the removal rule of `## Delivery` Step DL-5; `yes` keeps it (the drafts, evaluator reports, request and response bodies stay for inspection). A run that ended in an `ERROR:`, delivered a ticket with a `FAIL` verdict or wrote `overflow-findings.md` keeps it whatever the token says.
- `render=auto|off|excel|soffice`: whether an `.xlsx` source also gets an optional visual render to PDF, as `references/sources.md` **Sheet rendering (optional)** defines. Absent → `auto` (a workbook whose converter output shows a page-like structure is rendered by the first renderer this host has, else the run notes that no render exists); `off` never renders; `excel` or `soffice` forces that one renderer for every workbook source. Without an `.xlsx` source the token is accepted and has no effect.
- `depth=<tier>`: `standard`, `thorough` or `exhaustive`. Without it, the evidence depth that the rubric's depth-gated rules read follows each ticket's Size (`thorough` for `L` or `XL`, else `standard`); the token raises that depth, never lowers it (`references/ac-quality-criteria.md`, Terminology, Policy kill switch).
- `rounds=<N>`: the number of evaluation rounds per ticket in Phase 4, an integer from 1 to 5; absent → `3` (the initial evaluation and two revisions); `rounds=1` evaluates once and never revises. Each revision round re-spawns the planner with the latest draft and the latest Feedback, and the evaluator with the previous round's Feedback (`references/agent-spawn-prompts.md`, Phase 4).
- `max_tickets=<N>`: the most tickets one run creates, an integer from 1 to 30; absent → `20`. Every decomposer spawn carries it as the line `Max tickets: <N>`; work units beyond it are not lost: the decomposer returns `Status: partial` and the dropped units are written to `{scratch}/overflow-findings.md`, a findings document a later run takes with `findings=` (Step D-4).
- `constraint_<key>=off` (repeatable): turns off the rubric gate whose **Kill switch** names that key, for every ticket of the run. The keys are `oracle_verification` (Gate 7), `independent_evidence` (Gate 8), `failure_class_coverage` (Gate 9) and `peer_uniformity` (Gate 10); without the token every gate is active. Every planner and ticket-evaluator spawn carries the tokens as one `Constraints:` line (`references/agent-spawn-prompts.md`, Rules for every spawn prompt).

**Empty arguments**: when the request carries no description, no `brief=` / `findings=` token and no `source=` token, print `Usage: /create-ticket <ticket description> | brief=<path> | findings=<path> [source=<spec> ...] [source_auth_env=<VAR>] [source_auth_scheme=bearer|basic] [source_content_path=<jq path>] [destination=local:<dir> | mcp:<server>[/<tool>] | api:<url> | browser:<url> | cli:<command>] [auth_env=<VAR>] [auth_scheme=bearer|basic] [template=<path>] [id_path=<path>] [content_type=<media type>] [parent=<id>] [confirm=yes|no] [depth=<tier>] [rounds=<N>] [max_tickets=<N>] [keep_scratch=yes|no] [render=auto|off|excel|soffice] [constraint_<key>=off]` and stop, before any preflight.

Errors, each printed before anything else runs and followed by stop: an unknown destination kind (a value that starts with none of the five kinds and is not an `http://` or `https://` URL) → `ERROR: unknown destination kind in destination=<spec without query> (expected local:, mcp:, api:, browser: or cli:)`, where `<spec without query>` is the spec with everything from the first `?` removed, truncated to 80 characters (never the raw spec); `auth_env=`, `template=` or `id_path=` without an `api:` or `cli:` destination → `ERROR: auth_env=, template= and id_path= apply only to an api: or cli: destination`; `content_type=` without an `api:` destination → `ERROR: content_type= applies only to an api: destination`; `auth_scheme=` without an `api:` destination → `ERROR: auth_scheme= applies only to an api: destination`; another `auth_scheme=` value → `ERROR: auth_scheme= must be bearer or basic`; an `mcp_<name>=` token with neither an `mcp:` destination nor a destination URL without a kind (typed or named in prose) → `ERROR: mcp_<name>= applies only to an mcp: destination`; another `depth=` value → `ERROR: depth= must be standard, thorough or exhaustive`; another `confirm=` value → `ERROR: confirm= must be yes or no`; another `keep_scratch=` value → `ERROR: keep_scratch= must be yes or no`; another `render=` value → `ERROR: render= must be auto, off, excel or soffice`; a `rounds=` value other than an integer from 1 to 5 → `ERROR: rounds= must be an integer from 1 to 5`; a `max_tickets=` value other than an integer from 1 to 30 → `ERROR: max_tickets= must be an integer from 1 to 30`; an unknown source kind → `ERROR: unknown source kind in source=<spec without query> (expected file:, dir:, mcp:, api:, browser: or cli:)` (the spec truncated as for a destination); a `source=` value outside its pattern → `ERROR: source=<spec without query> contains characters this skill does not accept` (for a `source=file:` spec the query starts at its last `?`, as `references/sources.md` defines it); `source_auth_env=` without an `api:` source → `ERROR: source_auth_env= applies only to an api: source`; `source_content_path=` without an `api:` or `cli:` source → `ERROR: source_content_path= applies only to an api: or cli: source`; `source_auth_scheme=` without an `api:` source → `ERROR: source_auth_scheme= applies only to an api: source`; another `source_auth_scheme=` value → `ERROR: source_auth_scheme= must be bearer or basic`; `parent=` with a `local:` destination → `ERROR: parent= applies only to an mcp:, api:, browser: or cli: destination`; a `parent=` value outside its pattern → `ERROR: parent= contains characters this skill does not accept`; a `browser:` source or destination on a host with no browser tool (Host notes) → `ERROR: this host offers no browser tool; pass source=api:<url> or source=cli:<command>` (a source) or `ERROR: this host offers no browser tool; pass destination=api:<url> or destination=cli:<command>` (a destination); a `cli:` command that carries a literal token value → the `a credential in the command line; use $VAR` error of the **Character rule**; a `constraint_<key>=` token whose key is not one of the four above → `ERROR: unknown constraint key <key>`; a known key with a value other than `off` → `ERROR: constraint_<key>= accepts only off`. For the checks that tie an option to a source or destination kind, a kind-less `http://` or `https://` URL, typed or named in prose, counts as an `api:` or `cli:` source or destination, and a destination URL also as an `mcp:` destination for `mcp_<name>=` (its channel is derived later), so its options are accepted, and a typed `source_auth_env=`, `source_auth_scheme=`, `auth_env=`, `auth_scheme=` or `content_type=` keeps it on the API channel.

Then run the destination preflight of `references/destinations.md` (read-only: it creates nothing and writes nothing outside `{scratch}`) so an unusable destination fails before any agent runs; for a remote kind its last step stops the run when the request carries `confirm=no` and this host has no ask-user tool, because the confirmation before the first create could never be given (without a `confirm=` token such a host implies `confirm=yes`, `confirm=` above). When `confirm=yes` is implied, print `NOTE: this host has no ask-user tool; running as if confirm=yes was passed (a remote create is not confirmed first, and a ticket still graded FAIL is delivered as FAIL (unresolved)); pass confirm=no to stop instead` once, right after the preflight, for every destination kind; the run continues. Right after a successful preflight, in every mode (unless a derived output already created it right after the `Resolved:` and `Derived:` lines, **Platform item URLs** above, in which case that `{scratch}` is reused and these steps are not run again), create the run scratch directory inside the working directory with the shell tool running `mkdir -p .local/create-ticket-scratch` and then, as a second command, `mktemp -d .local/create-ticket-scratch/run.XXXXXX`, and record the path the second prints, relative to the working directory, as `{scratch}` (for example `.local/create-ticket-scratch/run.k3Qz9a`). If either command fails, print `ERROR: create-ticket cannot create the scratch directory .local/create-ticket-scratch/ in the working directory (<reason>)` and stop. It holds every transient file of the run (investigation, source dossier, drafts, evaluator reports, request and response bodies). It is removed as the last step of the run by the removal rule of `## Delivery` Step DL-5 (absent `keep_scratch=yes`, a run that ended cleanly: Delivery completed with no `ERROR:`, no ticket delivered with a `FAIL` verdict, no `overflow-findings.md`), and kept otherwise; that rule's `rm -r` and two `rmdir` commands are the only delete commands of this skill, and only the orchestrator runs them. It lives inside the working directory, never under a system temporary directory, because a host may confine the file-read and file-write tools of the orchestrator and of every subagent to the working directory, and a scratch outside it then cannot be written or cannot be read by the subagents. Then, right after the scratch directory is created and for every destination kind, when `git rev-parse --show-toplevel` succeeds, check whether the `.gitignore` at the repository root already holds the exact line `**/.local/*` with the shell tool running `grep -qxF '**/.local/*' "<root>/.gitignore"`, where `<root>` is the directory `git rev-parse --show-toplevel` printed: exit status 0 → nothing is written; any other status (no such line, or no such file) → append the line with the shell tool running `printf '%s\n' '**/.local/*' >> "<root>/.gitignore"`. Each is one command whatever the working directory (append only; the redirect creates the file when it does not exist; never rewrite, reorder or remove existing lines), so a run that stops early leaves no unignored file behind; outside a repository, skip this. The line ignores every `.local/` directory of the repository, so the default destination `local:.local/tickets` is ignored by git too (`references/destinations.md` `## local:<dir>`, **Keep the quarantine out of commits**). `{scratch}` is always a working-directory-relative path; it appears inside spawn prompts and, when it is kept, on the Final summary's `Scratch:` line, and is never written into a ticket or sent to a destination. Then, when the request carried `source=` tokens, run `## Intake` (every source is read into `{scratch}/sources/` and the dossier is built) before Phase 1; an Intake `ERROR:` stops the run with nothing delivered.
