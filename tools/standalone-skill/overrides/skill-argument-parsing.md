## Argument Parsing

This host passes no argument variable: the input is the user's request text, that is, the text of the message that invoked this skill (everything after `/create-ticket` when it was typed as a command). Parse it into one mode: `findings=<path>` (scan `findings=`); `brief=<path>` (scan `brief=`); else bare-description free-text. `source=<spec>` tokens (below) add inputs to any mode and may stand alone: a request made only of tokens with at least one `source=` is a bare-description run whose description Intake derives.

**Prose resolution**: the request may state its input and its output in prose, in any language, after the skill name (a statement naming material to read: a file, a directory, a workbook and a sheet of it, an item or page reachable through an MCP server of this session, a URL; or a statement naming where the tickets go: a directory, a platform reachable through an MCP server, an item there to attach them to, an endpoint). After the token scan (so every explicit token is known) and before any token is acted on, translate every such statement into the equivalent `source=`, `brief=`, `findings=`, `destination=`, `parent=` or `?sheet=` form by what the statement names, never by the wording of one language. Rules: an explicit token wins over a prose statement about the same thing; prose never sets `confirm=yes`, `depth=`, `render=` or `constraint_<key>=off`; a resolved value passes the same character rule and checks as a typed token; an item reachable through an MCP server that the statement names by title or URL instead of by identifier is looked up as `references/sources.md` `### An MCP item named in prose` defines (at most one read-only search call, an exact single match or a question), and a URL resolves as **Platform item URLs** below defines (`api:` of the URL as typed, unless the statement says to read it through an MCP server or the URL is the web address of an item whose platform's HTTP API the orchestrator knows); print one line `Resolved: <the tokens, an api: URL without its query string>` as the run's first output so the reading is visible before anything runs (omit the line when nothing was resolved); a statement that resolves two ways (two servers, two files of that name) or to nothing (a name that matches no file, no server, no tool) → ask the user with the ask-user tool; when it is unavailable, denied or erroring, `ERROR: cannot resolve the request's input or output statement: <statement>` and stop, never an assumption, because a wrong destination cannot be undone remotely. A Markdown file named by a prose input statement becomes `brief=` when the statement calls it a brief or its frontmatter (opened with the file-read tool) carries `slug`, `findings=` when the statement calls it findings or its frontmatter carries `findings_version`, and `source=file:` otherwise; any other file kind is always `source=file:`. The description is the request text with the resolved input and output statements removed (a resolved value never reaches `{parent-slug}` derivation); when nothing remains, the request counts as made of tokens only (Intake I-5 derives `{intent}`). A resolved value that contains whitespace, `?` or `&` is printed on the `Resolved:` line in double-quoted token form (`source="file:My Docs/a.xlsx?sheet=Open items"`); the line shows the reading, the run acts on the resolved values themselves and never re-parses the line, so a sheet name that token form could not carry is still passed to the converter whole.

**Platform item URLs**: a URL named by a prose statement is read in one of two ways, decided by the orchestrator from the URL and its own knowledge, never by the wording of one language. (a) The web address of an ITEM on a platform (a wiki page, a work item, an issue, a document page; illustrative only) whose HTTP API the orchestrator knows with confidence (for an input: the read endpoint of that item and where its content sits in the response; for an output: the create endpoint, the request-body shape, where the identifier sits in the response and how a new item is linked to an existing parent) → the derived form below. (b) Any other URL → `api:` of the URL as typed. When the statement says to read or deliver through an MCP server, or names one, the MCP rules above apply instead and nothing is derived. Nothing derived is ever a guess:

- **Derived input** (the statement names an item URL as material to read): `source=api:<read endpoint>`, a request whose response carries the item's content, plus `source_content_path=<jq path>` when the response is JSON and the content sits in one field, plus `source_auth_env=<VAR>` / `source_auth_scheme=<scheme>` when the platform requires a token (**Auth variables** below); `references/sources.md` `### A platform item named by URL in prose` holds the rest.
- **Derived output** (the statement names an item URL as where the tickets go, or as the item they are created under or as children of): `destination=api:<create endpoint>`, an endpoint that creates one item per `POST`; `template=<path>` where `<path>` is `{scratch}/template-derived.json`, a JSON request body the orchestrator writes with the file-write tool, holding `{title}` and `{body}` as whole string values and, when the statement named an item to create under, `{parent}` where the platform's API expects the parent link (`{parent}` may sit inside a longer string, such as a link URL that embeds the identifier; `references/destinations.md` `## api:<url>`); `id_path=<jq path>`; `parent=<id>`, the item's identifier taken from the URL, when the statement creates under it; `content_type=<media type>` when the endpoint needs a body media type other than `application/json`; `auth_env=<VAR>` / `auth_scheme=<scheme>` as below. A kind of item the statement names (as tasks, as issues, as sub-items; illustrative only) is carried into the derived endpoint or body as that platform's API expects; a statement naming none gets the platform's default kind, said on the `Derived:` line. In this case only, `{scratch}` is created right after the `Resolved:` and `Derived:` lines are printed (nothing is read or written before them), by the two commands and the `.gitignore` step of the scratch paragraph at the end of this section (its `ERROR:` included), and the template is written into it at once, before the non-interactive token check of **Auth variables** and before the destination preflight; the scratch paragraph then reuses that `{scratch}` instead of creating a second one, and the destination preflight, which runs after it, finds the file. Because the directory does not exist yet when the `Resolved:` and `Derived:` lines are printed, those two lines show the template as the literal `{scratch}/template-derived.json`; every later line that names it (the `needs a token` `ERROR:` of **Auth variables**, and the confirmation question of `references/destinations.md` and its `ERROR:`) prints the real path, `{scratch}` replaced by the recorded directory.
- **Derived URL rule**: a derived endpoint follows the `api:` URL rules of `references/destinations.md` (preflight steps 2 and 3: no whitespace, quote, backtick, `$`, backslash, `[`, `]`, `{` or `}`, and no credential in the URL); a path or query character those rules forbid is percent-encoded in the derived URL (a space as `%20`, `{` and `}` as `%7B` and `%7D`; illustrative only), never dropped. Query parameters, such as an API version parameter, are allowed.
- **Auth variables**: the orchestrator never invents an environment-variable name. A statement may name the variable that holds a token (a `$NAME`, or an identifier the statement calls a token, variable, secret or credential); the name becomes `source_auth_env=` when the statement is about reading, `auth_env=` when it is about delivering, and both when it says so or when both derived endpoints are on the same host; a typed `source_auth_env=` / `auth_env=` token counts as named. A named variable matches `^[A-Za-z_][A-Za-z0-9_]*$` like a typed one. When a derived endpoint's platform requires a token and no variable was named: interactive → ask for the variable's NAME with the ask-user tool (one question that names the endpoint's host; an answer that is not a name matching that pattern → the error below); non-interactive (the ask-user tool unavailable, denied or erroring) → `ERROR: <input|output> <item URL without query> needs a token; re-run with <every derived token of that direction, with auth_env=<VAR> (or source_auth_env=<VAR>) to fill in>` and stop. The question comes before the `Resolved:` line, so the answered name is printed on it; the error comes after the `Resolved:` and `Derived:` lines (and, for an output, after the derived template is written, so the re-run line names a file that exists) and before Intake and any preflight. The scheme (`bearer` by default, or `basic`) comes from the orchestrator's knowledge of the platform or from the statement.
- **Confidence floor**: a URL that reads as an item URL but whose platform's HTTP API the orchestrator does not know with confidence (any one derived value uncertain) is never guessed: interactive → ask with the ask-user tool whether to read it as a plain `GET` of the URL as typed (an input) or to supply `destination=api:<url> template=<path> id_path=<path>` (an output; the answered tokens count as typed); non-interactive (the ask-user tool unavailable, denied or erroring) → `ERROR: cannot derive the HTTP API for <host>; pass <the explicit tokens for that direction>` and stop, where the tokens are `source=api:<url> [source_content_path=<jq path>] [source_auth_env=<VAR>]` for an input and `destination=api:<url> template=<path> id_path=<path> [parent=<id>] [auth_env=<VAR>]` for an output.
- **Visibility**: the `Resolved:` line lists every derived token (`source=api:...`, `source_content_path=...`, `source_auth_env=...`, `source_auth_scheme=...`, `destination=api:...`, `template=...`, `id_path=...`, `parent=...`, `content_type=...`, `auth_env=...`, `auth_scheme=...`), each URL without its query string, each variable by its NAME only and a derived template as the literal `{scratch}/template-derived.json` (**Derived output** above). Directly after it, print one line per derived direction: `Derived: input from <item URL without query>: read endpoint <endpoint without query>, content field <jq path, or the whole body>[, token variable <VAR> (<scheme>)]` and `Derived: output from <item URL without query>: create endpoint <endpoint without query>, kind <kind>, parent <id>, body template {scratch}/template-derived.json[, content type <media type>][, token variable <VAR> (<scheme>)]` (no `parent` clause when no `parent=` was derived). Both lines are printed before Intake and before any preflight.
- **Precedence**: an explicit token wins over a derived value for the same thing: a typed `template=` replaces the derived template (nothing is written to `{scratch}/template-derived.json`, and `{scratch}` is then created only after the preflight, as usual), and a typed `destination=` means nothing is derived for the output. Prose, derived or not, never sets `confirm=yes`, `depth=`, `render=` or `constraint_<key>=off`.

**Character rule** (every path, directory, sheet name and identifier the request carries, typed or resolved): no double quote, backtick, `$`, backslash or control character; letters of any script are allowed; whitespace only inside a double-quoted token (`source="file:My Docs/a.xlsx"`, the quotes are not part of the value) or in a value resolved from prose. A value that breaks the rule → the `contains characters this skill does not accept` error of its token. URLs and environment-variable names keep their own stricter patterns.

**Mutual exclusion**: BOTH `brief=` AND `findings=` → print `ERROR: brief= and findings= are mutually exclusive. Pass exactly one.` and stop. Do NOT read either file. Do NOT touch the destination. Do NOT create directories. (Exact wording required: the literal `mutually exclusive`.)

**Input paths**: a `brief=` or `findings=` path may be absolute (it is the user's own file) and follows the character rule above; else print `ERROR: <token>= path contains characters this skill does not accept` and stop. Then check, here and only here (Steps F-1 and B-1 name this check's output), that the file exists with the file-read tool, never with a shell test, before the destination preflight: a missing findings file → `ERROR: Findings file not found at <path>`, a missing brief → `ERROR: Brief file not found at <path>`, and stop. Error lines and the Final summary echo the path exactly as the user typed it (Host notes).

**Option tokens**: scan the same text for these tokens (each runs to the next whitespace, so in a language written without word spaces put a space after the value) and remove them before the bare-description text is used:

- `destination=<spec>`: where Delivery puts the tickets. Absent → `local:.local/tickets`. The three kinds, `local:<dir>`, `mcp:<server>[/<tool>]` and `api:<url>`, and every check on them are defined in [references/destinations.md](references/destinations.md).
- `auth_env=<VAR>`, `template=<path>`, `id_path=<path>`: options of an `api:` destination only.
- `content_type=<media type>`, `auth_scheme=bearer|basic`: options of an `api:` destination only (the request body's media type, default `application/json`; how the `auth_env=` token is sent, default `bearer`).
- `mcp_<name>=<value>`: the value of a required parameter `<name>` of an `mcp:` destination's create tool (e.g. a project key; illustrative only).
- `source=<spec>` (repeatable): an input to read before Phase 1. The four kinds, `file:<path>` (a document, an `.xlsx` workbook read as a workbook, or a `.pdf` or image file transcribed through the file-read tool), `dir:<path>` (every supported file in a directory), `mcp:<server>/<tool>[?<name>=<value>...]` (one call of a read-only MCP tool) and `api:<url>` (one HTTP `GET`), their patterns, caps and `ERROR:` lines are defined in [references/sources.md](references/sources.md); the sequence is `## Intake`. One token may carry a comma-separated list of specs and a spec may omit its kind (a URL is `api:`, an existing directory `dir:`, any other path `file:`; `mcp:` is never inferred); both are resolved as `references/sources.md` `## Writing a source` defines, and the resolved specs are echoed on the `Resolved:` line.
- `source_auth_env=<VAR>`: an environment variable holding a token, for an `api:` source only (distinct from the destination's `auth_env=`; sent as a bearer token unless `source_auth_scheme=basic`).
- `source_content_path=<jq path>`, `source_auth_scheme=bearer|basic`: options of an `api:` source only (the field of a JSON response that holds the content; how the `source_auth_env=` token is sent, default `bearer`); like `source_auth_env=`, each applies to every `api:` source of the run.
- `parent=<id>`: an existing item of an `mcp:` or `api:` destination that every delivered ticket is linked to as its child (the parent is never modified); `<id>` follows the character rule above and contains no whitespace. How the link is set is defined per kind in [references/destinations.md](references/destinations.md).
- `confirm=yes`: skips the one confirmation question asked before the first `mcp:` / `api:` create; the only way to deliver to a remote destination in a non-interactive run.
- `render=auto|off|excel|soffice`: whether an `.xlsx` source also gets an optional visual render to PDF, as `references/sources.md` **Sheet rendering (optional)** defines. Absent → `auto` (a workbook whose converter output shows a page-like structure is rendered by the first renderer this host has, else the run notes that no render exists); `off` never renders; `excel` or `soffice` forces that one renderer for every workbook source. Without an `.xlsx` source the token is accepted and has no effect.
- `depth=<tier>`: `standard`, `thorough` or `exhaustive`. Without it, the evidence depth that the rubric's depth-gated rules read follows each ticket's Size (`thorough` for `L` or `XL`, else `standard`); the token raises that depth, never lowers it (`references/ac-quality-criteria.md`, Terminology, Policy kill switch).
- `constraint_<key>=off` (repeatable): turns off the rubric gate whose **Kill switch** names that key, for every ticket of the run. The keys are `oracle_verification` (Gate 7), `independent_evidence` (Gate 8), `failure_class_coverage` (Gate 9) and `peer_uniformity` (Gate 10); without the token every gate is active. Every planner and ticket-evaluator spawn carries the tokens as one `Constraints:` line (`references/agent-spawn-prompts.md`, Rules for every spawn prompt).

**Empty arguments**: when the request carries no description, no `brief=` / `findings=` token and no `source=` token, print `Usage: /create-ticket <ticket description> | brief=<path> | findings=<path> [source=<spec> ...] [source_auth_env=<VAR>] [source_auth_scheme=bearer|basic] [source_content_path=<jq path>] [destination=local:<dir> | mcp:<server>[/<tool>] | api:<url>] [auth_env=<VAR>] [auth_scheme=bearer|basic] [template=<path>] [id_path=<path>] [content_type=<media type>] [parent=<id>] [confirm=yes] [depth=<tier>] [render=auto|off|excel|soffice] [constraint_<key>=off]` and stop, before any preflight.

Errors, each printed before anything else runs and followed by stop: an unknown destination kind → `ERROR: unknown destination kind in destination=<spec without query> (expected local:, mcp: or api:)`, where `<spec without query>` is the spec with everything from the first `?` removed, truncated to 80 characters (never the raw spec); `auth_env=`, `template=` or `id_path=` without an `api:` destination → `ERROR: auth_env=, template= and id_path= apply only to an api: destination`; `content_type=` without an `api:` destination → `ERROR: content_type= applies only to an api: destination`; `auth_scheme=` without an `api:` destination → `ERROR: auth_scheme= applies only to an api: destination`; another `auth_scheme=` value → `ERROR: auth_scheme= must be bearer or basic`; an `mcp_<name>=` token without an `mcp:` destination → `ERROR: mcp_<name>= applies only to an mcp: destination`; another `depth=` value → `ERROR: depth= must be standard, thorough or exhaustive`; another `confirm=` value → `ERROR: confirm= accepts only yes`; another `render=` value → `ERROR: render= must be auto, off, excel or soffice`; an unknown source kind → `ERROR: unknown source kind in source=<spec without query> (expected file:, dir:, mcp: or api:)` (the spec truncated as for a destination); a `source=` value outside its pattern → `ERROR: source=<spec without query> contains characters this skill does not accept` (for a `source=file:` spec the query starts at its last `?`, as `references/sources.md` defines it); `source_auth_env=` without an `api:` source → `ERROR: source_auth_env= applies only to an api: source`; `source_content_path=` without an `api:` source → `ERROR: source_content_path= applies only to an api: source`; `source_auth_scheme=` without an `api:` source → `ERROR: source_auth_scheme= applies only to an api: source`; another `source_auth_scheme=` value → `ERROR: source_auth_scheme= must be bearer or basic`; `parent=` with a `local:` destination → `ERROR: parent= applies only to an mcp: or api: destination`; a `parent=` value outside its pattern → `ERROR: parent= contains characters this skill does not accept`; a `constraint_<key>=` token whose key is not one of the four above → `ERROR: unknown constraint key <key>`; a known key with a value other than `off` → `ERROR: constraint_<key>= accepts only off`.

Then run the destination preflight of `references/destinations.md` (read-only: it creates nothing) so an unusable destination fails before any agent runs. Right after a successful preflight, in every mode (unless a derived output already created it right after the `Resolved:` and `Derived:` lines, **Platform item URLs** above, in which case that `{scratch}` is kept and these steps are not run again), create the run scratch directory inside the working directory with the shell tool running `mkdir -p .create-ticket-scratch` and then, as a second command, `mktemp -d .create-ticket-scratch/run.XXXXXX`, and record the path the second prints, relative to the working directory, as `{scratch}` (for example `.create-ticket-scratch/run.k3Qz9a`). If either command fails, print `ERROR: create-ticket cannot create the scratch directory .create-ticket-scratch/ in the working directory (<reason>)` and stop. It holds every transient file of the run (investigation, source dossier, drafts, evaluator reports, request and response bodies) and is not removed at the end: this skill uses no delete command. It lives inside the working directory, never under a system temporary directory, because a host may confine the file-read and file-write tools of the orchestrator and of every subagent to the working directory, and a scratch outside it then cannot be written or cannot be read by the subagents. Then, when `git rev-parse --show-toplevel` succeeds, run `git check-ignore -q .create-ticket-scratch/x`; exit status 1 (not ignored) → append the line `.create-ticket-scratch/` to the `.gitignore` at the repository root with the shell tool running `printf '%s\n' ".create-ticket-scratch/" >> "<root>/.gitignore"`, where `<root>` is the directory `git rev-parse --show-toplevel` printed, so the command is one command whatever the working directory (append only; the redirect creates the file when it does not exist; never rewrite, reorder or remove existing lines), so a run that stops early leaves no unignored file behind; outside a repository, skip this. `{scratch}` is always a working-directory-relative path; it appears inside spawn prompts and on the Final summary's `Scratch:` line, and is never written into a ticket or sent to a destination. Then, when the request carried `source=` tokens, run `## Intake` (every source is read into `{scratch}/sources/` and the dossier is built) before Phase 1; an Intake `ERROR:` stops the run with nothing delivered.
