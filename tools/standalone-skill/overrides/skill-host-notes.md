## Host notes

This skill runs with no hooks installed, so these guarantees rest on these instructions alone:

- **Tool roles**: this skill names tools by role, never by a host's tool name. Before Phase 1, resolve each role once to one concrete tool of this host and use that tool wherever the role is named: the **file-read tool** (read a file), the **file-write tool** (create a file with given content), the **file-edit tool** (replace part of an existing file), the **search tools** (text search over file contents, and file lookup by name pattern), the **shell tool** (run a POSIX shell command; every command this skill names is POSIX), the **URL-fetch tool** (fetch a URL over HTTP; this skill never requires it, HTTP goes through the shell tool, and the role is named only where the roles are forbidden to use it), the **subagent tool** (run a prompt as a separate general-purpose subagent, the host's default agent type, and return its result) and the **ask-user tool** (put a question to the user and return the answer within the same run; ending the turn to ask in prose does not count). A role this host has no tool for: the subagent tool → the degraded branch of Mandatory role invocations; the ask-user tool → the non-interactive fallbacks; any other role except the URL-fetch tool → `ERROR: this host offers no <role>` and stop.
- **PII and secrets**: never write an absolute home path (a path that begins with the user's home directory) into any generated file, spawn prompt, ticket or summary. `{scratch}` (Argument Parsing) is always relative to the working directory (`.create-ticket-scratch/run.XXXXXX`) and so needs no exception; it appears inside spawn prompts, on the Final summary's `Scratch:` line and in the `(draft saved under {scratch})` suffix of two `ERROR:` lines. One exception: a `brief=` / `findings=` path is the user's own input and is echoed exactly as the user typed it in error lines and the Final summary. Neither is ever written into a ticket or sent to a destination. Pass the rubric as `{rubric_path}` (Pre-computed Context: `{skill_root}` as found, repository-relative or `~`-prefixed), never expanded. The same holds for secrets: the value of the variable an `api:` destination's `auth_env=` names, and any other token, never appears in a prompt, ticket, summary, error line or file; a shell command refers to it only as `$VAR` (see `references/destinations.md`).
- **Shell commands**: this skill declares no `allowed-tools`, so every shell command (`date`, `mktemp`, `mkdir`, `ls`, `mv`, `printf`, `git`, `command`, `curl`, `jq`, `python3` or its fallback `python` for a workbook source, and the shell builtins `[`, `echo` and `case` of the variable probes in `references/sources.md` and `references/destinations.md`) goes through the host's own permission prompt. Approve only the commands the steps above name. Every user-supplied path, directory, sheet name and identifier passes the character rule of Argument Parsing (no double quote, backtick, dollar, backslash or control character) before it reaches a double-quoted shell argument, so a name in any script is accepted and none can break out of its quotes.
- **File access and approvals**: the run scratch directory `{scratch}` lies inside the working directory, so a host that confines file access to the working directory needs no extra allowance for the run's own files, for the orchestrator or for a subagent; only a `brief=`, `findings=` or `source=` path the user typed, and `{skill_root}` under a personal skill root, may lie outside it and may need the host's approval. A host that pre-approves shell commands by their first word may refuse a command that joins several (`;`, `&&`, `|`, a loop); the scratch creation and the `.gitignore` append are written as single commands for that reason, while the variable probes of `references/sources.md` and `references/destinations.md` and the `api:` request pipe are joined by design and need the host's approval as a whole. With `confirm=yes`, the `api:` adapter's shell commands (`jq`, `curl`) still go through the host's permission prompts unless the host pre-approves them.
- **Sources are read-only**: Intake (`source=`) reads files, one MCP tool result and one HTTP body each, writes only under `{scratch}/sources/`, and never calls a tool whose description says it creates, updates, deletes, sends or posts; an `mcp:` source is refused when its tool reads as anything but retrieval. The caps (60,000 characters per source, 150,000 in total, 8,000 of excerpts per planner spawn) bound every spawn prompt; raise nothing without checking the host's context window.
- **Python 3 for `.xlsx` sources only**: a workbook is read by `scripts/xlsx_to_text.py` (standard library only, run as `python3 -I`); every other source kind needs no interpreter. Without Python 3 on the PATH an `.xlsx` source is an `ERROR`, nothing else changes.
- **Remote creates are not transactional**: an `mcp:` or `api:` destination cannot roll back, so a failure part-way leaves the items already created in place; the run prints their identifiers and stops (Step DL-4).
- **Evaluator independence**: the ticket-evaluator is hermetic by instruction only. A general-purpose subagent carries every tool; its prompt (`references/agents/ticket-evaluator.md`) forbids reading any file other than the ticket inlined in that prompt, and the orchestrator inlines both the ticket and the rubric so the evaluator never needs to.
