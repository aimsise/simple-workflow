## Host notes

This skill runs with no hooks installed, so these guarantees rest on these instructions alone:

- **Tool roles**: this skill names tools by role, never by a host's tool name. Before Phase 1, resolve each role once to one concrete tool of this host and use that tool wherever the role is named: the **file-read tool** (read a file), the **file-write tool** (create a file with given content), the **file-edit tool** (replace part of an existing file), the **search tools** (text search over file contents, and file lookup by name pattern), the **shell tool** (run a POSIX shell command; every command this skill names is POSIX), the **URL-fetch tool** (fetch a URL over HTTP; this skill never requires it, HTTP goes through the shell tool, and the role is named only where the roles are forbidden to use it), the **subagent tool** (run a prompt as a separate general-purpose subagent, the host's default agent type, and return its result), the **ask-user tool** (put a question to the user and return the answer within the same run; ending the turn to ask in prose does not count) and the **browser tool** (navigate to a URL, read the page's text, fill a field, click; present only when the session has such a tool, such as an MCP server that drives a browser; illustrative only; never required, and used only for a `browser:` source or destination, typed or derived). A role this host has no tool for: the subagent tool → the degraded branch of Mandatory role invocations; the ask-user tool → the non-interactive fallbacks and the implied `confirm=yes` (below); the browser tool → no `browser:` channel is ever a candidate of **Platform item URLs**, and a typed `browser:` token stops with `ERROR: this host offers no browser tool; pass source=api:<url> or source=cli:<command>` (a source) or `ERROR: this host offers no browser tool; pass destination=api:<url> or destination=cli:<command>` (a destination); any other role except the URL-fetch tool → `ERROR: this host offers no <role>` and stop. A run is non-interactive when this host has no ask-user tool or when asking is treated as deny (an ask-user tool that errors counts the same); every non-interactive fallback (the Phase 2 skip, the stops below) applies to both cases, but only the first, no ask-user tool at all, implies `confirm=yes` (Argument Parsing, `confirm=`): without a `confirm=` token such a host skips the confirmation before the first remote create and delivers a ticket still graded FAIL after its last round as `FAIL (unresolved)`, after printing `NOTE: this host has no ask-user tool; running as if confirm=yes was passed (a remote create is not confirmed first, and a ticket still graded FAIL is delivered as FAIL (unresolved)); pass confirm=no to stop instead` right after the destination preflight (repeated in the Final summary). Among the non-interactive fallbacks, a URL named in prose (or typed without a kind) whose channels need a sign-in nobody can give, a URL whose every channel failed, a typed `mcp:` destination's missing required parameter, a remote destination when nobody can confirm and `confirm=yes` is neither typed nor implied (with `confirm=no` and no ask-user tool, stopped by the last step of the destination preflight, before Phase 1), and a ticket still graded FAIL after its last round (`rounds=`) under the same condition stop with an `ERROR:` line that spells out the tokens to pass, so the line can be copied and completed (Argument Parsing, **Platform item URLs**; Phase 4, the exhausted-retry escalation). An ambiguous output statement, or a statement that resolves to nothing, stops with `ERROR: cannot resolve the request's input or output statement: <statement>` on such a host too: an implied `confirm=yes` answers no question but the two confirmations.
- **PII and secrets**: never write an absolute home path (a path that begins with the user's home directory) into any generated file, spawn prompt, ticket or summary. `{scratch}` (Argument Parsing) is always relative to the working directory (`.local/create-ticket-scratch/run.XXXXXX`) and so needs no exception; it appears inside spawn prompts, on the Final summary's `Scratch:` line when it is kept, and in the `(draft saved under {scratch})` suffix of two `ERROR:` lines. One exception: a `brief=`, `findings=`, `destination=local:` or `template=` path is the user's own input and is echoed exactly as the user typed it (with backslashes read as `/`) in error lines and the Final summary (a `~` prefix stays `~` and is never expanded in anything printed or recorded; **`~` paths** below). None of them is ever written into a ticket or sent to a destination. The one generated file that records such a path, `split-plan.md` (a `local:` destination with N > 1), writes `{dir}` in its `ticket_dir` lines as typed when it is relative or `~`-prefixed, and an absolute path under the home directory with that prefix written as `~`; never an expanded home path (`references/split-plan-schema.md`). Pass the rubric as `{rubric_path}` (Pre-computed Context: `{skill_root}` as found, repository-relative or `~`-prefixed), never expanded. The same holds for secrets: the value of the variable an `api:` destination's `auth_env=` names, and any other token, never appears in a prompt, ticket, summary, error line or file; a shell command refers to it only as `$VAR` (see `references/destinations.md`). The one-line output of a command-line client's status command (Argument Parsing, **Auth**) may name an account: it is shown on the terminal only and never written into the dossier, a ticket, the Final summary or a spawn prompt.
- **`~` paths**: this bullet is the one statement of the rule; every other file points here. A user path is printed and recorded in its normalized form, the path as typed with every backslash read as `/` (Argument Parsing, **Character rule**): that form is the one every later line uses (the `Resolved:` line, every `ERROR:` and `WARNING:` line, the Final summary, a source's `Origin:`), and "as typed" anywhere in this skill means it. A path that starts with `~` (a `source=`, `brief=`, `findings=`, `destination=local:` or `template=` path, a file a `dir:` source finds under one, a personal skill root of Pre-computed Context, and `{skill_root}` under one) keeps its `~` in everything printed or recorded and reaches a tool in one of two ways. A shell command, EVERY shell command that takes a user path (the existence tests `[ -e ]` and `[ -d ]`, `ls`, `mkdir`, `mv`, `git check-ignore`, the workbook converter and the sheet render, the NUL-byte text probe, `jq` on a `template=` file, and any other the steps name), gets it as `"$HOME/<the part after ~/>"`, the whole value inside one pair of double quotes (`$HOME` expands inside them, a `~` does not); such a command line is never written into a prompt, a ticket or a file. A file tool (the file-read, file-write or file-edit tool) gets the path as typed; when the tool reports it missing or cannot write it, retry once with the home directory expanded; the expanded form is never recorded or printed.
- **Shell commands**: this skill declares no `allowed-tools`, so every shell command (`date`, `mktemp`, `mkdir`, `ls`, `mv`, `printf`, `git`, `command`, `curl`, `jq`, `base64` and `tr` (only inside the `auth_scheme=basic` / `source_auth_scheme=basic` header pipeline of `references/sources.md` and `references/destinations.md`), `dd` and `od` (only inside the NUL-byte probe of a `file:` source of no listed kind, `references/sources.md`), `grep` (inside that NUL-byte probe, and for the `**/.local/*` `.gitignore` check of Argument Parsing), `rm` and `rmdir` (only for the removal of the run's own scratch directory at the end of a clean run, `## Delivery` Step DL-5: `rm -r "{scratch}"`, `rmdir .local/create-ticket-scratch`, `rmdir .local`, the only delete commands of this skill, run by the orchestrator alone), `python3` or its fallback `python` for a workbook source (the converter `python3 -I .../scripts/xlsx_to_text.py` and the optional render `python3 -I .../scripts/xlsx_render.py`), and the shell builtins `[`, `echo` and `case` of the variable probes in `references/sources.md` and `references/destinations.md`, plus the command of a `cli:` source or destination and the client's status or read probe) goes through the host's own permission prompt. Approve only the commands the steps above name, with one carve-out: a `cli:` command, typed or derived, runs as given and is printed in full before it runs, so the host's permission prompt for it is the user's gate (a typed command is the user's own; a derived one is a read for a source and one create per ticket for a destination, shown in the confirmation question first unless `confirm=yes` is typed or implied, and always printed on the `Resolved:` and `Derived:` lines). The render script in turn launches `osascript`, the Windows shell interpreter (powershell.exe) or `soffice` to drive a spreadsheet application or LibreOffice installed on the host; the host's prompt shows only the `python3` command, so approving the render command approves what it launches, and declining it (or `render=off`) only leaves the workbook without a render. Every user-supplied path, directory, sheet name and identifier passes the character rule of Argument Parsing (no double quote, backtick, dollar or control character, and no backslash outside a path value, where every backslash is first read as `/`) before it reaches a double-quoted shell argument, so a name in any script is accepted and none can break out of its quotes. A `cli:` command is exempt from that rule (Argument Parsing, **Character rule**): `$VAR` references are allowed and expanded by the shell, a literal token value never appears in the command, and control characters and newlines are refused.
- **File access and approvals**: the run scratch directory `{scratch}` lies inside the working directory, so a host that confines file access to the working directory needs no extra allowance for the run's own files, for the orchestrator or for a subagent; only a `brief=`, `findings=`, `source=`, `destination=local:` or `template=` path the user typed, and `{skill_root}` under a personal skill root, may lie outside it and may need the host's approval. A host that pre-approves shell commands by their first word may refuse a command that joins several (`;`, `&&`, `|`, a loop); the scratch creation, the `.gitignore` check and append, and the scratch removal are written as single commands for that reason, while the variable probes of `references/sources.md` and `references/destinations.md`, the `api:` request pipe and the text probe of a `file:` source (`dd ... | od ... | grep ...`) are joined by design and need the host's approval as a whole. With `confirm=yes`, typed or implied, the `api:` adapter's shell commands (`jq`, `curl`) still go through the host's permission prompts unless the host pre-approves them.
- **Sources are read-only**: Intake (`source=`) reads files, one MCP tool result, one HTTP body, one command's output and one page's text each (plus at most 20 follow-up reads of one platform item URL, Argument Parsing **Follow-up reads**), writes only under `{scratch}/sources/`, never calls a tool whose description says it creates, updates, deletes, sends or posts, and never clicks, fills or submits anything through the browser tool; an `mcp:` source is refused when its tool reads as anything but retrieval. The caps (60,000 characters per source, 150,000 in total with longer sources cut to fit, 8,000 of excerpts per planner spawn) bound every spawn prompt; raise nothing without checking the host's context window.
- **Python 3 for `.xlsx` sources only**: a workbook is read by `scripts/xlsx_to_text.py` (standard library only, run as `python3 -I`); every other source kind needs no interpreter. Without Python 3 on the PATH an `.xlsx` source is an `ERROR`, nothing else changes. The sheet render (`scripts/xlsx_render.py`, `render=`) is optional: it needs a spreadsheet application or LibreOffice on the host, and without one the source's `Rendered:` line says so and the run continues.
- **Remote creates are not transactional**: an `mcp:`, `api:`, `browser:` or `cli:` destination cannot roll back, so a failure part-way leaves the items already created in place; the run prints their identifiers and stops (Step DL-4).
- **Evaluator independence**: the ticket-evaluator is hermetic by instruction only. A general-purpose subagent carries every tool; its prompt (`references/agents/ticket-evaluator.md`) forbids reading any file other than the ticket inlined in that prompt, and the orchestrator inlines both the ticket and the rubric so the evaluator never needs to.
