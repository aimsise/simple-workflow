## Host notes

This skill runs with no hooks installed, so these guarantees rest on these instructions alone:

- **Tool roles**: this skill names tools by role, never by a host's tool name. Before Phase 1, resolve each role once to one concrete tool of this host and use that tool wherever the role is named: the **file-read tool** (read a file), the **file-write tool** (create a file with given content), the **file-edit tool** (replace part of an existing file), the **search tools** (text search over file contents, and file lookup by name pattern), the **shell tool** (run a shell command; every command this skill names is written in its POSIX form, and **Shell dialect** below says which form runs), the **URL-fetch tool** (fetch a URL over HTTP; this skill never requires it, HTTP goes through the shell tool, and the role is named only where the roles are forbidden to use it), the **subagent tool** (run a prompt as a separate general-purpose subagent, the host's default agent type, and return its result), the **ask-user tool** (put a question to the user and return the answer within the same run; ending the turn to ask in prose does not count) and the **browser tool** (navigate to a URL, read the page's text, fill a field, click; present only when the session has such a tool, such as an MCP server that drives a browser; illustrative only; never required, and used only for a `browser:` source or destination, typed or derived). A role this host has no tool for: the subagent tool → the degraded branch of Mandatory role invocations; the ask-user tool → the non-interactive fallbacks and the implied `confirm=yes` (below); the browser tool → no `browser:` channel is ever a candidate of **Platform item URLs**, and a typed `browser:` token stops with `ERROR: this host offers no browser tool; pass source=api:<url> or source=cli:<command>` (a source) or `ERROR: this host offers no browser tool; pass destination=api:<url> or destination=cli:<command>` (a destination); the search tools → the shell tool does each search the steps name, read-only and one file per command: it lists the matching lines of one file with `grep -nE '<pattern>' "<file>"`, or `grep -nF -e '<text>' "<file>"` for a fixed string (the **Heading check** and the logical-id search of `references/destinations.md`, the **Section check** of `references/agent-spawn-prompts.md`, the `Change rationale:` lines of Step DL-2, the heading lookup of the **Stored text check**), and lists a directory with `ls -1A "<dir>"`. Under PowerShell the forms PS-HN-1 to PS-HN-3 of `references/shell-powershell.md` do these searches (with .NET calls, where `Select-String` would read a file in the console's code page); they write the lines they find to `{scratch}/shell-result.txt` (for the listing of a `dir:` source, `{scratch}/sources/shell-result.txt`), the one file a search writes, which is read with the file-read tool before the next search replaces it; before `{scratch}` exists, when nothing may be written yet (the lookups of **Prose resolution**, Argument Parsing), the shell tool instead tests each path a statement names with PS-SRC-1 and PS-SRC-2 and lists no directory; any other role except the URL-fetch tool → `ERROR: this host offers no <role>` and stop. A run is non-interactive when this host has no ask-user tool or when asking is treated as deny (an ask-user tool that errors counts the same); every non-interactive fallback (the Phase 2 skip, the stops below) applies to both cases, but only the first, no ask-user tool at all, implies `confirm=yes` (Argument Parsing, `confirm=`): without a `confirm=` token such a host skips the confirmation before the first remote create and delivers a ticket still graded FAIL after its last round as `FAIL (unresolved)`, after printing `NOTE: this host has no ask-user tool; running as if confirm=yes was passed (a remote create is not confirmed first, and a ticket still graded FAIL is delivered as FAIL (unresolved)); pass confirm=no to stop instead` right after the destination preflight (repeated in the Final summary). Among the non-interactive fallbacks, a URL named in prose (or typed without a kind) whose channels need a sign-in nobody can give, a URL whose every channel failed, a typed `mcp:` destination's missing required parameter, a remote destination when nobody can confirm and `confirm=yes` is neither typed nor implied (with `confirm=no` and no ask-user tool, stopped by the last step of the destination preflight, before Phase 1), and a ticket still graded FAIL after its last round (`rounds=`) under the same condition stop with an `ERROR:` line that spells out the tokens to pass, so the line can be copied and completed (Argument Parsing, **Platform item URLs**; Phase 4, the exhausted-retry escalation). An ambiguous output statement, or a statement that resolves to nothing, stops with `ERROR: cannot resolve the request's input or output statement: <statement>` on such a host too: an implied `confirm=yes` answers no question but the two confirmations.
- **PII and secrets**: never write an absolute home path (a path that begins with the user's home directory) into any generated file, spawn prompt, ticket or summary. Whether a path begins with the home directory is decided after every backslash of both is read as `/`, case-insensitively on a host whose file system ignores case, and for every spelling the host uses for the home directory (illustrative only: a drive-letter form); wherever this skill writes such a path, that prefix is written `~`. `{scratch}` (Argument Parsing) is always relative to the working directory (`.local/create-ticket-scratch/run.XXXXXX`) and so needs no exception; it appears inside spawn prompts, on the Final summary's `Scratch:` line when it is kept, and in the `(draft saved under {scratch})` suffix of two `ERROR:` lines. One exception: a `brief=`, `findings=`, `destination=local:` or `template=` path is the user's own input and is echoed exactly as the user typed it (with backslashes read as `/`) in error lines and the Final summary (a `~` prefix stays `~` and is never expanded in anything printed or recorded; **`~` paths** below). None of them is ever written into a ticket or sent to a destination. The one generated file that records such a path, `split-plan.md` (a `local:` destination with N > 1), writes `{dir}` in its `ticket_dir` lines as typed when it is relative or `~`-prefixed, and an absolute path under the home directory with that prefix written as `~`; never an expanded home path (`references/split-plan-schema.md`). Pass the rubric as `{rubric_path}` (Pre-computed Context: `{skill_root}` as found, repository-relative or `~`-prefixed), never expanded. The same holds for secrets: the value of the variable an `api:` destination's `auth_env=` names, and any other token, never appears in a prompt, ticket, summary, error line or file; a shell command refers to it only as `$VAR` (see `references/destinations.md`). The one-line output of a command-line client's status command (Argument Parsing, **Auth**) may name an account: it is shown on the terminal only and never written into the dossier, a ticket, the Final summary or a spawn prompt.
- **`~` paths**: this bullet is the one statement of the rule; every other file points here. A user path is printed and recorded in its normalized form, the path as typed with every backslash read as `/` (Argument Parsing, **Character rule**): that form is the one every later line uses (the `Resolved:` line, every `ERROR:` and `WARNING:` line, the Final summary, a source's `Origin:`), and "as typed" anywhere in this skill means it. A path that starts with `~` (a `source=`, `brief=`, `findings=`, `destination=local:` or `template=` path, a file a `dir:` source finds under one, a personal skill root of Pre-computed Context, and `{skill_root}` under one) keeps its `~` in everything printed or recorded and reaches a tool in one of two ways. A shell command, EVERY shell command that takes a user path (the existence tests `[ -e ]` and `[ -d ]`, `ls`, `mkdir`, `mv`, `git check-ignore`, the workbook converter and the sheet render, the NUL-byte text probe, `jq` on a `template=` file, and any other the steps name), gets it as `"$HOME/<the part after ~/>"`, the whole value inside one pair of double quotes (`$HOME` expands inside them, a `~` does not; the spelling is the same under PowerShell); such a command line is never written into a prompt, a ticket or a file. A file tool (the file-read, file-write or file-edit tool) gets the path as typed; when the tool reports it missing or cannot write it, retry once with the home directory expanded; the expanded form is never recorded or printed.
- **Shell dialect**: Pre-computed Context records the dialect of the shell tool on its `Shell:` line. With `Shell: posix` every command runs in the POSIX form this skill prints. With a `Shell: powershell <n>` line NEVER run a POSIX form: several of its command names are aliases of other commands there (`rm`, `rmdir`, `ls`, `cp`, `mv` and `curl` among them), and one of them, `rmdir` on a directory that is not empty, can delete the directory with its content. Run instead the PowerShell form that `references/shell-powershell.md` lists under its id for that step. It writes the files its POSIX form writes (and, for text it does not print, the one file its entry names), and for each outcome the step reads from an exit status it prints a token (such as `exit=0`, `missing` or `present`), so the step takes the branch that the entry maps the token to. A command the file does not list (a `cli:` command, a client's status command) is written by the general rules at the top of that file, never run unchanged. Under PowerShell an `api:` source or destination needs `curl.exe`, which current Windows ships, and neither `jq` nor Python; the Python scripts run as in a POSIX shell when Python 3 is present.
- **Shell commands**: this skill declares no `allowed-tools`, so every shell command (`date`, `mktemp`, `mkdir`, `ls`, `mv` (only for the quarantine of a failed `local:` write, `references/destinations.md`, run as `command mv`), `cp` (only to copy a ticket's draft or final text into `{scratch}` or into its `local:` ticket directory, `## Delivery` Step DL-2 and `references/destinations.md`, run as `command cp`), `sed` (only for the two content-field conversions of `references/destinations.md` **Content-field markup**), `printf`, `git`, `command` (the program-presence test `command -v`, and `command cp` and `command mv`, which run the programs `cp` and `mv` and never an alias of them), `curl`, `jq`, `base64` and `tr` (only inside the `basic` / `basic-token` header pipelines of `auth_scheme=` and `source_auth_scheme=` in `references/sources.md` and `references/destinations.md`), `dd` and `od` (only inside the NUL-byte probe of a `file:` source of no listed kind, `references/sources.md`), `grep` (inside that NUL-byte probe, for the `**/.local/*` `.gitignore` check of Argument Parsing, and for the searches of a host with no search tool, **Tool roles** above), `rm` and `rmdir` (only for the removal of the run's own scratch directory at the end of a clean run, `## Delivery` Step DL-5: `rm -rf "{scratch}"`, `rmdir .local/create-ticket-scratch`, `rmdir .local`, the only delete commands of this skill, run by the orchestrator alone), the Python 3 interpreter `{python}`, which is `python3`, `python` or `py -3` (`py`), whichever the interpreter rule of `references/sources.md` `## file:<path>` chose after running each with `--version` (the workbook converter `{python} -I .../scripts/xlsx_to_text.py` and the optional render `{python} -I .../scripts/xlsx_render.py` for a workbook source, and `{python} -I .../scripts/ticket_body.py` for the HTML conversion and the stored-text check of a remote destination), and the shell builtins `[`, `echo` and `case` of the variable probes in `references/sources.md` and `references/destinations.md` and of the existence tests `[ -e "<root>/.gitignore" ]` of Argument Parsing and `[ -d "{scratch}" ]` of Step DL-5, plus the command of a `cli:` source or destination and the client's status or read probe) goes through the host's own permission prompt. Approve only the commands the steps above name, with one carve-out: a `cli:` command, typed or derived, runs as given and is printed in full before it runs, so the host's permission prompt for it is the user's gate (a typed command is the user's own; a derived one is a read for a source and one create per ticket for a destination, shown in the confirmation question first unless `confirm=yes` is typed or implied, and always printed on the `Resolved:` and `Derived:` lines). Under PowerShell the commands to approve are the forms of `references/shell-powershell.md`, each in place of the POSIX command its entry quotes: the cmdlets `Get-ChildItem`, `Get-Command`, `Test-Path`, `New-Object`, `Select-Object`, `Out-String`, `ConvertFrom-Json` and `ConvertTo-Json`, `Remove-Item` only in the scratch removal, .NET calls, `git`, `curl.exe` and the Python interpreter. The render script in turn launches `osascript`, the Windows shell interpreter (powershell.exe) or `soffice` to drive a spreadsheet application or LibreOffice installed on the host; the host's prompt shows only the `{python}` command, so approving the render command approves what it launches, and declining it (or `render=off`) only leaves the workbook without a render. Every user-supplied path, directory, sheet name and identifier passes the character rule of Argument Parsing (no double quote, backtick, dollar or control character, and no backslash outside a path value, where every backslash is first read as `/`) before it reaches a double-quoted shell argument, so a name in any script is accepted and none can break out of its quotes. A `cli:` command is exempt from that rule (Argument Parsing, **Character rule**): `$VAR` references are allowed and expanded by the shell, a literal token value never appears in the command, and control characters and newlines are refused.
- **File access and approvals**: the run scratch directory `{scratch}` lies inside the working directory, so a host that confines file access to the working directory needs no extra allowance for the run's own files, for the orchestrator or for a subagent; only a `brief=`, `findings=`, `source=`, `destination=local:` or `template=` path the user typed, and `{skill_root}` under a personal skill root, may lie outside it and may need the host's approval. A host that pre-approves shell commands by their first word may refuse a command that joins several (`;`, `&&`, `|`, a loop); the scratch creation, the interpreter choice (`<name> --version`), the `.gitignore` check, existence test and append, the copies (`command cp`), the `markdown-escaped` conversion (`sed ... >| ...`), the `ticket_body.py` commands and the scratch removal with its existence test are written as single commands for that reason, while the variable probes of `references/sources.md` and `references/destinations.md`, the `api:` request pipes (the `basic` and `basic-token` ones included), the preformatted HTML fallback (`{ printf ...; sed ...; printf ...; } >| ...`) and the text probe of a `file:` source (`dd ... | od ... | grep ...`) are joined by design and need the host's approval as a whole. Under PowerShell only the forms that `references/shell-powershell.md` marks one statement are single commands (the time, a skill-root listing, the program test, the variable probes and the existence tests); every other form is one script block, `& { ... }`, that joins several statements and needs the host's approval as a whole. With `confirm=yes`, typed or implied, the `api:` adapter's shell commands (`jq`, `curl`) still go through the host's permission prompts unless the host pre-approves them.
- **Login-shell options**: the shell tool may run a login shell whose options and aliases change plain commands (a no-clobber option that refuses `>` onto an existing file and may refuse `>>` onto a missing one, a pattern that matches nothing raised as an error, `rm`, `cp` or `mv` aliased to a form that asks before it overwrites or deletes). Every form this skill prints is written to run unchanged there: a redirection onto a file that may already exist (a rebuilt or converted body, a request, a captured output) is `>|` (and `2>|`), a `.gitignore` line is appended with `>>` only to a file the existence test found and written with `>` only when it found none (Argument Parsing), `cp` and `mv` run as `command cp` and `command mv`, the scratch removal is `rm -rf`, and the number-collision listing of `references/destinations.md` reads an unmatched-pattern error as no match. A command run this way prints on its standard output exactly what it prints in a plain shell; the only other output is that error line of the collision listing.
- **Sources are read-only**: Intake (`source=`) reads files, one MCP tool result, one HTTP body, one command's output and one page's text each (plus at most 20 follow-up reads of one platform item URL, Argument Parsing **Follow-up reads**), writes only under `{scratch}/sources/`, never calls a tool whose description says it creates, updates, deletes, sends or posts, and never clicks, fills or submits anything through the browser tool; an `mcp:` source is refused when its tool reads as anything but retrieval. A `cli:` command the user typed is the one input the skill does not check: it runs as given, printed in full first, through the host's permission prompt. The caps (60,000 characters per source, 150,000 in total with longer sources cut to fit, 8,000 of excerpts per planner spawn) bound every spawn prompt; raise nothing without checking the host's context window.
- **Python 3, required for `.xlsx` sources only**: a workbook is read by `scripts/xlsx_to_text.py` (standard library only, run as `{python} -I`, the interpreter `references/sources.md` `## file:<path>` chooses); every other source kind needs no interpreter. Without Python 3 an `.xlsx` source is an `ERROR`. Delivery uses it when present: `scripts/ticket_body.py` (standard library only) converts a ticket to HTML for `body_format=html` and runs the **Stored text check** of `references/destinations.md`; without it the HTML body is sent as preformatted text (with a `NOTE:`) and the check compares the heading titles only. The sheet render (`scripts/xlsx_render.py`, `render=`) is optional: it needs a spreadsheet application or LibreOffice on the host, and without one the source's `Rendered:` line says so and the run continues.
- **Remote creates are not transactional**: an `mcp:`, `api:`, `browser:` or `cli:` destination cannot roll back, so a failure part-way leaves the items already created in place; the run prints their identifiers and stops (Step DL-4).
- **Evaluator independence**: the ticket-evaluator is hermetic by instruction only. A general-purpose subagent carries every tool; its prompt (`references/agents/ticket-evaluator.md`) forbids reading any file other than the ticket inlined in that prompt, and the orchestrator inlines both the ticket and the rubric so the evaluator never needs to.
