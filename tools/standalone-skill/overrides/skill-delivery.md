## Delivery

**One destination.** A run delivers to exactly one destination. When the destination is not `local:`, no `ticket.md`, `split-plan.md` or counter file is written anywhere, and the default `.local/tickets` directory is never created. For a destination other than `local:`, no copy of any ticket is saved to a local file (not under `.local/tickets`, not anywhere else outside `{scratch}`), not even as a backup or for reference. The default `local:.local/tickets` applies only when the request carries neither a `destination=` token nor an output statement; a request that states an output which cannot be resolved or reached stops with its `ERROR:` line and never falls back to the default.

All three modes converge here, and only once every ticket of the run has a verdict. Exactly four verdicts exist: `PASS` (Phase 4); `SELF-EVALUATED` (only on a host with no subagent tool at all, per the degraded branch above); `FAIL (user-accepted)` (the user chose "proceed" at the exhausted-retry question); `FAIL (unresolved)` (`confirm=yes`, typed or implied on a host with no ask-user tool, stood in for the user at the exhausted-retry question, so nobody reviewed the remaining issues). A subagent spawn of any mandatory role that failed and then failed its one retry (Mandatory role invocations) fails the run instead: nothing is delivered. Producing the tickets (Phases 1-4) never depends on the destination; Delivery is the only part of the run that writes outside `{scratch}`, apart from the `**/.local/*` `.gitignore` check and append of Argument Parsing. The destination is `destination=<spec>` from Argument Parsing (`local:.local/tickets` only when the request carries neither a `destination=` token nor an output statement), already checked by its preflight; each kind's adapter (`local:`, `mcp:`, `api:`, `browser:`, `cli:`) is defined in [references/destinations.md](references/destinations.md). Ticket content follows [references/ticket-template.md](references/ticket-template.md); the summary format is in [references/write-path-templates.md](references/write-path-templates.md).

### Step DL-1: Dependency graph validation (N>1 only)

Re-verify the `depends_on` graph: every `depends_on` references another ticket's logical id (`{parent-slug}-part-{M}` for `1 ≤ M ≤ N`); acyclic (topological sort returns N nodes). Violation → `ERROR: split-plan validation failed — <reason>` or `ERROR: circular dependency detected among tickets: <cycle members>`. The topological order computed here is the delivery order of every later step, so a ticket's dependencies are always delivered before it.

### Step DL-2: Final ticket text

For each ticket `i` (its 0-based position in the topological order of Step DL-1, `i` = `0..N-1`; the same `i` names every `{scratch}/<name>-{i}.<ext>` file of Delivery and of [references/destinations.md](references/destinations.md)), the final ticket text is the file `{scratch}/final-{i}.md`, built by copy and edit and never written out by the orchestrator (**Whole text, never re-typed**, [references/destinations.md](references/destinations.md) `## Rules for every destination`):

1. **Copy.** The shell tool running `cp "<draft file>" "{scratch}/final-{i}.md"` (one single command), where `<draft file>` is the ticket's last evaluated draft: the draft file whose text its last evaluator round graded, as Phase 4 recorded it (**Graded draft**), by the path the orchestrator named in that planner's spawn prompt, never a path taken from a subagent's return text.
2. **Edit in place**, with the file-edit tool only, one targeted replacement per change:
   - Remove every `Change rationale:` line the retry planner added (a line that starts with `Change rationale:`, or an HTML comment that contains it, removed from its `<!--` through its own `-->` and no further); the rest of the text is delivered unchanged.
   - Add `| Quality | <verdict> |` to its field table, with the verdict exactly as named above.
   - If `brief=<path>` provided: read brief `slug` → `{brief_slug}`, the brief's original value even when `{parent-slug}` is its normalized form (Step B-2); extract `{brief_part}` from any "This is part {N} of {total}" indicator (from split briefs). Add `| Brief Slug | {brief_slug} |` (key `brief_slug`) and (if extracted) `| Brief Part | {brief_part} |` (key `brief_part`).

Every later step starts from this file: the adapter of the destination copies it again (`ticket.md` of `local:`, `{scratch}/body-{i}.md` of a remote kind) and edits only the heading, the `Dependencies` cell, the logical ids and the `Depends on:` line, and the **Heading check** of [references/destinations.md](references/destinations.md) compares the file it delivers with the last evaluated draft before any create, and for `local:` before `split-plan.md` and the counter are written.

### Step DL-3: Deliver each ticket

Run the adapter of the destination kind over the tickets in topological order, exactly as [references/destinations.md](references/destinations.md) specifies:

- **Identity is destination-assigned.** A ticket's heading becomes `## {id}: {Title}`. A `local:` destination allocates `{id}` = `T-{NNN}` from its counter before it writes anything; an `mcp:`, `api:`, `browser:` or `cli:` destination submits the body with the heading `## {Title}` and records the `{id}` its create call, create command or resulting page returns.
- **Dependencies** are written as destination identifiers: the ticket's `Dependencies` cell lists the `{id}` of each ticket it depends on (`--` when none). A `local:` destination knows every `T-{NNN}` before writing; an `mcp:`, `api:`, `browser:` or `cli:` destination knows them because each dependency was created earlier in topological order, and it also states them as the destination's own link field or a `Depends on:` line.
- **`local:`** writes `{dir}/{parent-slug}/{NNN}-{slug}/ticket.md` per ticket, a copy of `{scratch}/final-{i}.md` edited in place (**Whole text, never re-typed**, [references/destinations.md](references/destinations.md)), plus `{dir}/{parent-slug}/split-plan.md` when N > 1 ([references/split-plan-schema.md](references/split-plan-schema.md)), then writes the counter `{dir}/.ticket-counter` once, after every other file is written.
- **`mcp:`, `api:`, `browser:` and `cli:`** are remote: they ask once for confirmation before the first create, the question naming the channel and, for a destination derived from a platform item URL, every derived value (skipped only by `confirm=yes`, typed or implied: on a host with no ask-user tool and no `confirm=` token it is implied and the question is skipped, while with `confirm=no` the destination preflight has already stopped the run; a "no" stops it with `ERROR: remote delivery declined; nothing created`, and an erroring or denied ask-user tool with the `needs an interactive confirmation` `ERROR:`; nothing is created either way), then issue one create per ticket: a tool call, a `POST`, one run of the command template, or one submit of the create form. Each sends the sent body of **Content-field markup** in [references/destinations.md](references/destinations.md): `{scratch}/body-{i}.md`, a copy of `{scratch}/final-{i}.md` in which every logical id (`{parent-slug}-part-N`) of an already-created ticket is replaced by that ticket's destination id (from the highest part number down, whole ids only: **Logical ids**), converted by a program when `body_format=` asks for another markup. After each create, the **Stored text check** reads back what the platform stored and stops the run on an incomplete text. The returned identifiers are the whole record of the run: no split-plan file and no counter.

### Step DL-4: Delivery failure

- **`local:`**: a write failure is quarantined, never deleted, under `{dir}/.rollback/{parent-slug}-{ts}/` by the write-failure rule of [references/destinations.md](references/destinations.md); the counter stays untouched, so a re-run with the same inputs is safe. If only the final counter write fails, the tickets stay in place and the run prints `ERROR: create-ticket counter write failed — set {dir}/.ticket-counter to <counter + N> (<reason>)` and stops. Two runs that deliver to the same `{dir}` at the same time are not serialized by a lock; they are detected instead: a ticket number already used under another parent refuses the write, and a counter that changed between its read and its write stops the run with `ERROR: create-ticket counter changed during delivery — ...` ([references/destinations.md](references/destinations.md), Delivery steps 3 and 6).
- **`mcp:` / `api:` / `browser:` / `cli:`**: remote creates are not transactional. On a failure after `k` successful creates (a **Stored text check** that reports `incomplete` included, its item counted among them), print the `k` identifiers already created (in creation order), then the `ERROR:` line, and stop. Never delete or modify a remote item, never retry on your own and never fall through to another access channel once a create was attempted (the item may exist): a re-run with the same input creates every ticket again, so the user decides how to finish.

### Step DL-5: Final summary

**Scratch removal** (the last step of the run, after the Final summary values are known and before the Final summary is printed). The run scratch directory `{scratch}` is removed only when ALL of these hold: `keep_scratch` is `no` (Argument Parsing; the default); Delivery completed with no `ERROR:`; no ticket's verdict is `FAIL (user-accepted)` or `FAIL (unresolved)`; the decomposer did not return `Status: partial` (no `{scratch}/overflow-findings.md`). Otherwise it is kept, so the drafts, evaluator reports, request and response bodies and the overflow findings stay available, and every `(draft saved under {scratch})` suffix and the overflow `findings=` re-run hint stay true. The removal runs these commands with the shell tool, each a single command, in this order: `rm -rf "{scratch}"`, where `{scratch}` is exactly the relative path `mktemp` printed for this run (never a user-derived path, never a path with `..`, never an absolute path, never a glob; the `-f` keeps a login shell that aliases `rm` to an interactive form from asking a question nobody answers and removing nothing); then the existence test `[ -d "{scratch}" ]`, whose exit status 0 means the directory is still there; then `rmdir .local/create-ticket-scratch`; then `rmdir .local`. `rmdir` removes only an empty directory: a non-zero exit of either `rmdir` (the directory still holds another run or the tickets) is expected and ignored silently. A directory that is still there after `rm -rf` (exit status 0 of the existence test; `rm -rf` itself may exit 0 without removing everything) prints `WARNING: could not remove the scratch directory <{scratch}> (<reason>)` (repeated in the Final summary; `<reason>` is the error output of `rm -rf`, or `still present`), and the run still succeeds. `rm -rf` and the two `rmdir` commands are the only delete commands of this skill, and only the orchestrator runs them; no role ever runs a delete command.

End the run with a `### Final summary` block as the last output, in the format of [references/write-path-templates.md](references/write-path-templates.md). The `### Final summary` block is printed in that stated format, with its literal heading and its `Destination:` and `Scratch:` lines (each in the variants that carry it), and is never replaced by a free-form recap. It holds: per ticket, the path of its `ticket.md` (`local:`: relative to the working directory, or under `{dir}` as typed when `{dir}` is absolute or `~`-prefixed) or its identifier (`mcp:` / `api:` / `browser:` / `cli:`), plus category, size, AC count and verdict; N>1 adds the dependency order (and, for `local:`, the `split-plan.md` path); a remote destination adds the `Body:` line (the `body_format=` value used and the outcomes of the **Stored text check**). Repeat any `WARNING:` line of the run (e.g. the decomposer overflow, a normalized slug, a spawn retry, a retry draft that dropped sections, a `dir:` or follow-up read stopped at the 50-source cap, a `dir:` with directories below 5 levels, an ignored `body_format=`, a stored text that differs slightly, a scratch directory that could not be removed) and every `NOTE:` line of the run (the implied confirmation of Argument Parsing, `confirm=`; no Python 3 for the HTML conversion or for the stored-text check; a stored text that could not be read back). In every variant, the `Scratch:` line says what became of `{scratch}`: `Scratch: removed` when the removal above removed it; `Scratch: <{scratch} path> (kept: <reason>)` when it was kept, where `<reason>` is the first that applies of `keep_scratch=yes`, `error`, `a ticket was delivered with a FAIL verdict` and `overflow findings`, so the user can find the drafts, evaluator reports and API responses of the run; after a removal that left the directory in place, `Scratch: <{scratch} path> (kept: removal failed)`. The line is omitted when the run stopped before the scratch directory was created. On failure, list what was created (`Created: none`, or the `k` identifiers, then the `Body:` line) followed by the `ERROR:` line, which names the quarantine path when a `local:` write failed or its **Heading check** refused a ticket. Do not recommend follow-up commands.
